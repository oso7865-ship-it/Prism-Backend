# 07. SECURITY BASELINE

> 목적: 일반 하네스에서 모든 프로젝트에 공통으로 적용할 최소 보안 기준을 정의한다.  

---

## 1. 최소 보안 원칙

| 원칙 | 설명 |
|---|---|
| 비밀값 하드코딩 금지 | API Key, JWT Secret, DB Password를 코드/문서에 직접 쓰지 않음 |
| 개인 경로 노출 금지 | `C:\Users\...`, `/Users/...`, `/home/...` 같은 개인 절대경로 주의 |
| 권한은 서버에서 판단 | 프론트 표시 여부만으로 권한을 판단하지 않음 |
| 결제 금액은 서버 기준 | 클라이언트가 보낸 금액을 신뢰하지 않음 |
| 실패 흐름을 설계 | 성공 케이스만 구현하지 않음 |
| 외부 스크립트 검토 | 설치 스크립트, Hook, MCP 설정을 바로 실행하지 않음 |

---

## 2. 민감 기능 분류

이 표는 민감도 등급 분류만 소유한다. **어떤 Gate를 몇 개 함께 적용하는지는 전부 `08.QUALITY_GATE.md`의 §7-2 표를 본다** — 이 표는 Gate 이름을 나열하지 않는다(외부 검수 D-01).

| 등급 | 기능 |
|---|---|
| High | 결제, 환불, 정산 |
| High | 관리자 권한, 로그인/토큰 |
| Medium | 개인정보 수정, 파일 업로드, 주문 상태 변경 |
| Low | 단순 조회, 공개 페이지, 정적 문서 |

## 3. 보안 검수 기본 질문

```txt
1. 이 API는 인증이 필요한가?
2. 현재 사용자가 이 리소스를 수정할 권한이 있는가?
3. 요청값을 서버에서 다시 검증하는가?
4. 실패했을 때 상태가 잘못 바뀌지 않는가?
5. 같은 요청을 여러 번 보내도 안전한가?
6. 로그에 민감정보가 남지 않는가?
7. 외부 서비스 응답을 무조건 신뢰하지 않는가?
```

---

## 4. 결제/보안 Red-Blue 사고방식

| 역할 | 결제 하네스에서의 의미 |
|---|---|
| Red | 금액 변조, orderId 바꿔치기, 중복 요청, 웹훅 위조 등 악용 시나리오 작성 |
| Blue | 서버 금액 검증, 권한 검증, 상태 전이 제한, 로그/테스트 설계 |
| Purple | 발견된 문제를 체크리스트, 테스트, Gate 규칙으로 고정 |

---

## 5. PASS/WARN/FAIL 기준

| 판정 | 기준 |
|---|---|
| PASS | 민감정보, 권한, 입력값, 실패 흐름에 대한 필수 통제가 실제로 충족되어 있고, 미해결 고위험 항목이 없음(단순히 "검토했다"는 것만으로는 PASS가 아니다) |
| WARN | 직접 위험은 낮지만 검증 근거가 부족함, 또는 외부 서비스 응답을 사용하면서 인증성/무결성/타임아웃/실패 정책 중 일부만 정의됨 |
| FAIL | 비밀값 노출, 권한 누락, 결제 금액 신뢰, 민감 로그 노출이 있음. 또는 외부 서비스 응답을 사용하는데 인증성·무결성 검증이나 실패 시 처리 정책이 전혀 없음(외부 연동이 없으면 N/A) |

---

## 6. 금지 패턴

| 패턴 | 이유 |
|---|---|
| `amount`를 프론트 요청값 그대로 승인 | 금액 변조 가능 |
| 사용자 ID를 요청 body만 믿고 처리 | 타 사용자 리소스 접근 가능 |
| 결제 성공 전에 주문 상태를 확정 | 실패/중복 상태 꼬임 가능 |
| 외부 서비스 응답을 검증 없이 그대로 신뢰 | 응답 위조·변조·타임아웃 시 잘못된 상태로 이어질 수 있음 |
| 토큰/비밀번호를 로그에 출력 | 민감정보 노출 |
| 외부 Hook을 검토 없이 자동 실행 | 공급망 위험 |
