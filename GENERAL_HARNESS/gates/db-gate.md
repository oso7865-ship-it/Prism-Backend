# DB Gate

> 대상: ERD, DB 스키마, CREATE TABLE 문서, 인덱스 설계  
> 전역 원칙: 특정 DBMS에 종속되지 않는다. MySQL, PostgreSQL 등은 예시로만 사용한다.

## 1. 필수 항목

| 항목 | 설명 |
|---|---|
| PK | 모든 핵심 테이블은 기본키가 있어야 함 |
| FK/관계 설명 | 관계가 있는 컬럼은 FK 또는 관계 설명이 있어야 함 |
| 필수값 | NOT NULL 또는 필수 데이터 기준이 명확해야 함 |
| 유일성 | 이메일, 전화번호, 주문번호 등 중복 방지 기준이 있어야 함 |
| 상태값 | status 컬럼은 허용 값과 전이 기준이 있어야 함 |
| 삭제 정책 | Soft Delete/Hard Delete 사용 여부가 일관되어야 함 |
| 시간 컬럼 | 생성/수정 시각 기준이 있어야 함 |
| 금액/수량 | 단위, 타입, 음수 허용 여부가 명확해야 함 |

## 1-1. 권장 항목(필수 아님, 없어도 PASS를 막지 않지만 완전히 없으면 WARN 대상)

| 항목 | 설명 |
|---|---|
| Index | 조회 조건이 많은 컬럼은 인덱스 후보로 기록하는 것을 권장함(외부 검수 M-04/X-04 — 예전엔 §1 "필수 항목" 표에 있으면서 PASS는 필수로 안 치는 모순이 있었다) |


### 1-1. DB 기준 우선순위

ERD, DB 문서, 실제 스키마가 동시에 존재하면 아래 순서로 판단한다.

| 우선순위 | 기준 | 처리 |
|---:|---|---|
| 1 | 실제 운영/개발 DB 스키마 또는 마이그레이션 파일 | 현재 구현 기준. 변경 전 영향 범위 확인 필요 |
| 2 | 확정 DB Schema 문서 | 실제 스키마와 다르면 차이를 Report에 기록하고 확인 필요 |
| 3 | 확정 ERD | 설계 기준. 실제 스키마 반영 여부 확인 필요 |
| 4 | 후보 ERD/후보 스키마 | 초안. 구현 기준으로 사용 전 Confirm 필요 |

후보 ERD와 실제 DB 기준이 충돌하면 실제 DB 또는 마이그레이션 파일을 우선 확인한다. 실제 DB를 바꾸는 작업은 `04.GATEGUARD.md`의 DB/데이터 위험 작업 기준을 따른다.

## 2. PASS/WARN/FAIL

| 판정 | 기준 |
|---|---|
| PASS | PK/FK 또는 관계 설명, 필수값(NOT NULL), 유일성, 상태값, 삭제정책, 시간컬럼, 금액·수량 기준이 일관됨. Index 후보는 없어도 PASS를 막지 않는다(권장 사항) |
| WARN | Index 후보가 일부 또는 전부 없음, 제약조건·DBMS별 표현 설명이 부족함 |
| FAIL | PK 없음, 관계 불명확, 필수값 기준 없음, 중복 방지가 필요한 컬럼에 유일성 기준 없음, 상태값 기준 없음, 삭제 정책(Soft/Hard) 선택 안 됨, 시간 컬럼 기준 없음, 금액·수량 컬럼 의미 불명확(단위·타입·음수 허용 여부 없음) |

## 3. DB 검수 흐름

```mermaid
flowchart LR
    A[요구사항] --> B[테이블 도출]
    B --> C[PK/FK 또는 관계 설명 확인]
    C --> D[상태값/삭제정책 확인]
    D --> E[금액/시간/인덱스 후보 확인]
    E --> F[DB Gate 판정]
```

요약: 요구사항에서 테이블을 도출하고, 식별자·관계·상태·삭제·시간·금액·인덱스 기준을 검수한다.
