# 10. ADR

> 한국어 별칭: 아키텍처 결정 기록  
> 목적: 하네스의 중요한 구조적 결정을 기록한다.  
> 원칙: ADR은 작업 절차 문서가 아니라, 되돌리기 어려운 결정과 그 이유를 남기는 기록 문서다.

---

## ADR 작성 규칙

- ADR 번호는 문서 전체에서 고유해야 한다.
- 새 결정은 가장 마지막 ADR 번호 다음 번호를 사용한다.
- 기존 ADR 번호는 다른 결정을 위해 재사용하지 않는다.
- 번호를 수정한 경우 관련 Report와 Working Context의 참조도 함께 확인한다.
- 어떤 ADR의 결정이 이후 ADR로 대체되면, 상태를 `Accepted`에서 `Superseded by ADR-NNN`으로 바꾼다. 오래된 ADR을 지우지 않고 상태만 갱신한다(외부 검수 m-04).
- ADR의 여러 결정 중 **일부만** 후속 ADR이 바꾸면 전체를 `Superseded`로 표시하지 않는다. `Partially superseded by ADR-NNN (해당 부분만 한 줄 설명)`으로 표시해, 나머지 결정은 여전히 유효하다는 것을 명확히 한다(외부 검수 G-07).

## ADR-013. 외부 반입 후보는 재작성해서 필요한 부분만 반입한다

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 배경 | `harness_import_candidates_20260704`(ECC, Understand-Anything, codebase-memory-mcp에서 선별한 후보 자료)가 제공됨. 원본은 npm/TypeScript 전제, Hook 자동화, 실행자 분기(Executor Boot와 별도 에이전트 문서) 등 현재 하네스 전제와 다른 부분을 포함함 |

| 이유 | `00.HARNESS_RULES.md §2-2`의 원본 직접 복제 금지 원칙과, 특정 스택에 종속되지 않는다는 일반 하네스 원칙을 지키기 위함. 실행자 분기 구조는 SRS 전용 용어(Source of Truth, Stop Condition 등)를 전제해 현재 문서 세트의 용어 체계와 충돌할 수 있어 별도 검토가 필요함 |
| 결과 | 활성 스킬이 8개에서 10개로 늘었고, `02.SKILL_INDEX.md`에 스킬 대분류가 추가됨. 반입하지 않은 항목은 `_PENDING_IMPORT_LIST.md`에 사유와 함께 보존함 |

## ADR-014. 구조 WARN을 정식 WARN 분류로 유지한다

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 배경 | `DOCUMENT_AUDIT_REPORT.md`에서 `08.QUALITY_GATE.md`의 WARN 3분류와 하위 문서의 2분류 처리 기준이 충돌한다고 지적됨 |
| 결정 | `구조 WARN`을 삭제하지 않고 `일반 WARN` / `구조 WARN` / `위험 WARN` 3분류로 유지한다. 구조 WARN은 문서 연결, 스킬 인계, 번호 체계, 폴더 구조, 하네스 연결 구조가 모호한 경우에 사용하며, 일반 WARN처럼 바로 진행하지 않는다. |
| 이유 | 하네스 자체 수정과 문서 연결 변경은 파일 삭제나 DB 변경만큼 즉시 위험하지는 않지만, Source of Truth와 Handoff 흐름을 흔들 수 있으므로 별도 분류가 필요하다. |
| 결과 | `00.QUICK_REF.md`, `04.GATEGUARD.md`, `08.QUALITY_GATE.md`, 5개 Checklist에 구조 WARN 처리 기준을 동기화했다. |

## ADR-015. 혼합 운영 분기는 기존 Workflow와 Context Budget 안에서 처리한다

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 배경 | 혼합 운영(Claude+Codex) 관련 외부 검수 피드백에서 Claude + Codex 혼합 운영 전제와 실행자별 First Reading 경로가 충분히 고정되어 있지 않다고 지적됨. 피드백 원본 문서는 현재 보존되어 있지 않으며 반영 결과만 근거로 남긴다 |

| 이유 | 일반 하네스의 문서 수를 불필요하게 늘리지 않고, Claude형 문서 판단 Agent와 Codex형 로컬 실행 Agent의 책임 경계만 명확히 하기 위함이다. |
| 결과 | 별도 실행자 분기 구조는 `_PENDING_IMPORT_LIST.md`에 장기 보류로 유지하되, 현재 혼합 운영에 필요한 최소 규칙은 기존 문서 안에서 사용할 수 있다. |

## ADR-016. 하네스 이름을 GLOBAL_AI_HARNESS에서 GENERAL_HARNESS로 바꾼다

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 배경 | 사용자가 "글로벌 하네스"라는 이름 대신 담백한 "일반 하네스"로 바꾸길 원함 |
| 결정 | 폴더명/zip명/패키지명은 `GENERAL_HARNESS`(영문)로, 문서 내 한국어 표현은 "일반 하네스"로 통일한다. 한글 폴더명은 터미널/CLI 도구(특히 Codex 같은 로컬 실행 Agent)에서 경로 처리가 도구마다 다르게 깨질 수 있어 사용하지 않는다. |
| 이유 | 이름을 화려하게 짓지 않는다는 방향은 유지하되, 실제 파일시스템에 닿는 이름은 영문으로 두어 혼합 운영(Claude+Codex)에서의 경로 안전성을 확보하기 위함이다. |
| 결과 | `GLOBAL_AI_HARNESS` 문자열과 "전역 하네스" 표현을 활성 문서 22개에서 일괄 치환했다. `reports/` 안의 과거(리네임 이전) Report는 당시 이름을 그대로 보존해 증거로 남긴다. |

## ADR-017. 외부 참고자료(Understand-Anything, codebase-memory-mcp)에서 개념만 재작성 반입한다

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 배경 | `Understand-Anything`, `codebase-memory-mcp` 원본 저장소를 검토한 결과, 둘 다 설치형 완제품(모노레포/네이티브 바이너리, `curl \| bash` 설치)이라 직접 반입 대상은 아니지만, 각각에 재사용 가치가 있는 패턴이 있었다. |
| 결정 | Understand-Anything의 `docs/superpowers/specs`·`plans`에서 반복 확인된 "Goal/Non-Goals/Task 분해" 계획 패턴을 재작성해 `skills/planning/SKILL.md`로 신설한다. codebase-memory-mcp의 `check-no-test-skips.sh` 원칙("전제 조건 미비로 인한 SKIP은 FAIL이다")을 `skills/verification-loop/SKILL.md`에 반영한다. ECC 참고자료의 `validate-no-personal-paths.js` 아이디어를 `scripts/validate-no-personal-paths.mjs`로 재작성 반입한다. 두 저장소의 실제 코드/바이너리/설치 스크립트는 반입하지 않는다. |
| 이유 | `00.HARNESS_RULES.md §2-2`의 원본 직접 복제 금지 원칙, 외부 설치 스크립트 실행을 기본값으로 두지 않는다는 원칙을 지키면서도, 지난 검수에서 확인된 공백("코드 작성 전 계획 없음", "SKIP을 FAIL로 처리하지 않음", "개인 경로 노출 규칙이 문서에만 있고 자동 검사가 없음")을 메우기 위함이다. |

## ADR-029. 다섯 번째 외부 검수(2026-07-12) Critical 4건 반영

| 상태 | Accepted |

## ADR-031. archive Report 원본 삭제 결정 (§12 마지막 결정, 제3의 선택지)

| 상태 | Accepted (단, "고아 행 검사를 삭제일 cutoff로 판단" 부분은 `Partially superseded by ADR-032` — 날짜 기반 추정이 같은 날 추가된 진짜 고아를 못 잡는 결함이 실제로 재현되어 명시적 파일 목록 방식으로 교체됨. 삭제 결정 자체와 삭제 로그 개념은 유효) |

## ADR-032. 고아 행 검사의 날짜 cutoff 방식을 명시적 파일 목록 방식으로 교체

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 배경 | ADR-031에서 만든 "삭제 로그 날짜 이후 항목만 고아 검사" 로직에, `HISTORY_DIGEST.md`에 삭제일(2026-07-12)과 **같은 날짜**로 실제 존재하지 않는 파일(`2026-07-12_same-day-missing-probe_report.md`)을 가리키는 행을 추가해 검증한 결과, `validate-report-consistency.mjs`가 이를 못 잡고 PASS를 반환하는 것이 실제로 재현됨. 원인은 `dateMatch[1] > purgeCutoff`처럼 **엄격한 초과 비교**를 써서, cutoff와 같은 날짜는 "cutoff 이전"으로 취급돼 검사 대상에서 빠졌기 때문 |
| 결정 | 날짜 기반 추정을 완전히 폐기하고, `HISTORY_DIGEST.md`의 `<!-- PURGED_FILES_START -->` ~ `<!-- PURGED_FILES_END -->` 사이에 **실제로 삭제된 30개 파일명을 전부 명시적으로 나열**한다. `scripts/validate-report-consistency.mjs`는 이 목록에 있는 파일명만 "삭제 확인됨"으로 인정하고, 목록에 없는 고아 행은 날짜와 무관하게 전부 경고한다. 정상 상태(PASS)와 오염된 상태(동일한 probe 행 추가 시 WARN 발생) 둘 다 재현·확인했다 |
| 이유 | 날짜 같은 하루 단위 정보로는 "이 항목이 그때 삭제된 30개 중 하나인지"와 "이 항목이 그날 이후 새로 생긴 진짜 문제인지"를 구분할 수 없다. 명시적 목록은 이 모호함 자체를 없앤다 — 파일명이 목록에 있으면 삭제가 맞고, 없으면 무조건 의심 대상이다 |
| 결과 | 같은 문제가 세 번째로 반복되는 것을 막았다("자기 참조 문서/검사 로직의 갱신 누락·모호한 추정" 계열 — `04.GATEGUARD.md §11-3`의 기존 패턴과 같은 계열). 이 삭제 로그 방식은 이후 새로운 삭제가 생길 때마다 파일명을 목록에 그대로 추가하는 식으로 확장한다. `Partially superseded by ADR-033` — 명시적 목록 자체의 구조적 무결성(marker 유일성, 목록⊆digest, 목록∩archive=∅, count 일치, 연도 일반화)은 이후 강화됨. |

## ADR-033. 여섯 번째 외부 검수(재검수) Major 10건 반영 — 게시 트랜잭션·Gate 라우팅·검증 로직 정합화

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 배경 | 여섯 번째 외부 검수(재검수, 첨부 ZIP 52개 파일 독립 대조, Critical 0건)가 Major 10건을 지적했다: (M-01) Report 트랜잭션이 validator FAIL만 롤백, I/O 실패는 미대응, (M-02) project Report 완료 경로가 §8-2와 직접 충돌, (M-03) 복합 Gate 흐름도가 여전히 단일 분기, (M-04) API/DB/Payment Gate 필수-판정 1:1 재발, (M-05) Verification·Gate·Checklist 전역 최종판정 공식 없음, (M-06) 지난 라운드에 만든 PURGED_FILES 명시 목록도 연도 하드코딩·부분문자열 검사·자기승인 우회가 가능, (M-07) 구조 WARN이 게시를 막지 못함, (M-08) archive 삭제 예외가 다른 문서에 전파 안 됨, (M-09) Source Mapping의 4차 이후 provenance 누락과 5차 wildcard, (M-10) 직전 Report의 43/44 수치 차이와 "다음 작업 없음" 오류. M-06은 실제로 3가지 공격 시나리오(2027년 고아, 무단 목록 추가, 개수 조작)로 재현 테스트해 확인함 |
| 결정 | M-01: 트랜잭션 9번 단계로 I/O 실패도 validator FAIL과 동일 롤백. M-02: `06.REPORT_TEMPLATE.md §8-3`(프로젝트 Report 전용, ZIP 없음) 신설. M-03: 흐름도를 fan-out 구조로 재설계. M-04: API/DB/Payment Gate PASS/FAIL을 필수 항목과 완전히 재정렬. M-05: 전역 최종판정 공식(`maxSeverity(Verification, Gate 전부, Checklist 전부)`) 신설, 5개 Checklist "결과 요약"을 로컬 판정으로 재정의. M-06: `validate-report-consistency.mjs`를 digest 표 구조적 파싱 + marker 유일성 + 집합 연산(purged⊆digest, purged∩archive=∅) + count 일치 + 연도 일반화로 전면 재작성. M-07: 트랜잭션에 WARN 분류·해제 단계 추가. M-08: 삭제 예외를 4개 문서에 전파. M-09: Source Mapping에 4~6차 provenance 보강. M-10: 원본은 불변, 이 Report에 정정 기록만 남김 |
| 이유 | M-06은 지난 라운드(ADR-032)에 만든 "명시적 목록" 방식도 완벽하지 않다는 것을 보여준다 — 목록 자체의 구조적 무결성(형식, 중복, 다른 집합과의 관계, 개수 일치)까지 검증해야 진짜 안전하다. M-01~M-05, M-07은 "검증에 성공해도 게시를 막지 못하거나(WARN), 트랜잭션이 일부 실패 유형만 다루거나(I/O), 여러 판정 소스가 있는데 통합 규칙이 없는" 계열의 문제로, 전부 "부분적으로만 정의된 안전장치는 결국 우회된다"는 하나의 교훈으로 수렴한다 |
| 결과 | Major 10건 + Minor 5건, 총 15건 반영 완료. `scripts/validate-report-consistency.mjs`의 새 로직을 4가지 시나리오(정상/2027고아/무단추가/개수불일치)로 재현 테스트. 이 과정에서 마커 카운트 정규식 자체의 버그(설명 문구 속 마커 이름 언급까지 세어 정상 상태도 FAIL 오판)를 발견해 즉시 수정. `Partially superseded by ADR-034` — M-06의 "명시적 단일 목록" 방식은 이후 event 기반 구조로 대체됨(승인 자기결속·다중 삭제 지원). |

## ADR-034. 일곱 번째 외부 검수(재검수) Major 9건 반영 — 삭제 이벤트 모델, 나머지 잔여 정합화

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 배경 | 일곱 번째 외부 검수(재검수, Critical 0건, 첨부 ZIP 53개 파일 독립 대조)가 Major 9건을 지적했다. 가장 심각한 것은 M-06/X-06 — 지난 라운드(ADR-033)의 "명시적 목록" 방식도 "digest 행+목록+누계 count를 함께 조정"하면 새 승인 없이 조용히 통과하고(자기승인 우회를 실제로 재현해 확인), 반대로 정상적인 두 번째 삭제 이벤트는 오히려 실패시켰다(단일 누계 count 하나뿐이라 새 이벤트를 더하면 옛 count와 안 맞음). 그 외 M-01(초안 롤백 누락), M-02(§8-3 참조 잔존 오류, 첫 프로젝트 전환 미정의), M-03(외부연동 Security 우회, 계약Gate에 Verification 강제 없음), M-04(DB Index 필수·PASS·WARN 중첩), M-05(Release 비밀값 분리, Payment 로그의 §2/결과요약 불일치), M-07(06 §8-1 자체가 "이동만" 단정), M-08(SourceMapping 5·6차 통계가 서로 뒤바뀜), M-09(직전 Report의 44/45 오차, 이전 정정에서도 반복됨) |
| 결정 | M-06: 삭제를 "이벤트"로 구조화 — `HISTORY_DIGEST.md`에 `PURGE_EVENT`(event_id/date/approval/count를 헤더에 갖는 독립 블록)를 도입하고 기존 이벤트는 절대 고치지 않고 새 이벤트만 추가한다. `scripts/validate-report-consistency.mjs`가 각 이벤트를 독립 검증(event_id 유일성, count-목록 일치, approval이 실제 ADR인지, 목록이 digest 부분집합인지, archive와 안 겹치는지)한다. 5가지 시나리오(정상/정상 2차삭제/자기승인 시도/가짜ADR인용/중복ID)로 재현 테스트 완료. M-01: 미게시 초안도 롤백·격리 대상으로 명시. M-02: 188행 참조를 §8-3으로 교체, 첫 프로젝트 전환 시 하네스 Report는 그대로 두는 분기 추가. M-03: 비민감 경로도 외부연동 확인을 거치도록 흐름도 수정, 계약 Gate 전체에 "실제 코드 있으면 verification-loop 항상 누적" 규칙 추가. M-04: DB Index를 필수 항목 표에서 분리해 별도 "권장 항목" 절로 이동. M-05: Release §2 FAIL 목록에 비밀값 분리 반영, Payment Checklist PASS에 로그 기록 명시. M-07: §8-1의 "이동만" 단정을 retained/purged 두 상태로 재서술, 05.WORKING_CONTEXT §4에도 반영. M-08: Source Mapping의 5·6차 통계 뒤바뀜 정정. M-09: 이 Report 자체 |
| 이유 | M-06은 "명시적 목록도 완벽하지 않다"를 두 번째로 보여준 사례다 — 이번엔 "목록 내용을 검증"하는 것만으로는 부족하고 "그 목록이 시간에 따라 어떻게 변해야 하는지"(불변 이벤트 누적)까지 구조로 강제해야 한다는 교훈을 얻었다. 이건 근본적으로 "파일 기반 시스템은 쓰기 권한이 있는 누구나 과거 기록을 고칠 수 있다"는 한계를 완전히 없애지 못하지만, 최소한 "그냥 숫자 하나 바꾸기"보다 "새 불변 이벤트를 명시적으로 추가하기"가 훨씬 눈에 띄는 행위가 되도록 만들었다 |
| 결과 | Major 9건 전부 반영. 삭제 이벤트 모델을 5가지 시나리오로 직접 테스트(정상/정상 2차삭제/자기승인 시도/가짜ADR/중복ID 전부 기대대로 동작). Minor 5건도 함께 반영(검증기 개수 하드코딩 잔여, Quality Gate 노드명/참조 오류, Payment 로그 로컬 경계, Checklist 필드명, report-consistency PASS 문구 정확화). |

## ADR-035. 게시 트랜잭션에 "실제 전달" 단계 명시 — 자체 검수 7회차(반복루프 4회차)

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 배경 | Claude가 4회차 자체 검수(용어 전수 정리)를 마치고 검증·원자적 교체까지 전부 정상 수행했는데, 그 산출물을 실제 사용자에게 전달하는 것 자체를 깜빡했다. 사용자가 "왜 수정한 하네스를 안 보내주냐"고 물어서야 발견됨. `06.REPORT_TEMPLATE.md §8-2`를 확인한 결과, 이 절차가 "임시 zip 생성 → 검증 → 원자적 교체"까지만 규정하고 "그 산출물을 실제로 사용자에게 건네는 것"은 어디에도 명시돼 있지 않았다(`09.AGENT_WORKFLOW.md`, `00.HARNESS_RULES.md`, `04.GATEGUARD.md` 전체 grep으로도 확인) |
| 결정 | `06.REPORT_TEMPLATE.md §8-2`의 7번(원자적 교체) 뒤에 7-1번을 신설해 "산출물을 출력 위치로 복사 → 실제 전달 조치 → 전달한 파일이 검증한 후보와 동일한지 재확인 → 최종 결과를 전달 메시지에 기록"을 게시 절차의 정식 마지막 단계로 명시한다 |
| 이유 | 이 문서 세트가 그동안 정성 들여 만들어온 안전장치(검증 후 게시, 원자적 교체, WARN 해제 확인 등)는 전부 "패키지 파일 자체의 무결성"을 지키는 데는 완벽했지만, "그 결과를 실제로 사용자 손에 쥐어주는 마지막 한 걸음"은 암묵적 기대로만 남아 있었다. 그리고 그 암묵적 기대가 실제로 깨졌다 — 추론이 아니라 실제로 일어난 실패다 |
| 결과 | `06.REPORT_TEMPLATE.md §8-2`에 7-1번이 추가됨. 앞으로 게시 트랜잭션은 "패키지가 안전하게 만들어졌는가"뿐 아니라 "그 패키지가 실제로 사용자에게 도착했는가"까지 확인해야 완료로 본다. |

## ADR-036. `ui-ux-design` 스킬 신규 추가 — 스킬 본체와 기술 스택 정책의 분리 확정

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 배경 | 화면 설계(UI/UX) 작업을 정식 스킬로 등록해달라는 외부 검수 의견을 받았다. 검수 의견에는 두 가지 성격이 섞여 있었다 — (a) 스킬 자체를 어떻게 안전하게 구조화할지에 대한 제안(수용)과 (b) 검수 대상 ZIP 자체가 배포 오류 상태라는 전제(실제로는 검수자가 `CLAUDE.md`와 `GENERAL_HARNESS/`를 직접 합쳐 만든 별도 테스트용 zip이었고, 이 하네스가 실제로 배포한 zip과는 무관함이 SHA-256 대조로 확인됨). 후자는 거절하고 전자만 반영했다 |
| 결정 | `skills/ui-ux-design/SKILL.md`(기술 중립적 실행 절차)와 `skills/ui-ux-design/STACK_PROFILE_PRIMEVUE_TAILWIND.md`(PrimeVue+Tailwind 고정 정책, 프로젝트가 선택적으로 활성화)를 분리해 신설했다. `gates/ui-ux-gate.md`, `checklists/ui-ux-checklist.md`도 함께 신설했다. `08.QUALITY_GATE.md §7-2` 매트릭스에 화면 설계 관련 행(일반/로그인/관리자/개인정보/결제 화면)을 추가했다. `02.SKILL_INDEX.md`에 13번째 Active 스킬로 등록했다 |
| 이유 | 이 하네스는 이미 "프로젝트 전용 규칙을 전역 스킬로 고정하지 않는다"는 원칙(`_PENDING_IMPORT_LIST.md`의 `frontend-patterns` 제외 사유, `skill-scout`의 Anti-Pattern)을 갖고 있었다. PrimeVue/Tailwind처럼 이번 프로젝트에만 해당하는 기술 선택을 스킬 본체에 하드코딩하면 이 원칙과 정면으로 부딪힌다. Stack Profile을 별도 파일로 분리해 "스킬은 절차를 소유하고, 기술 정책은 선택적으로 활성화되는 별도 문서가 소유한다"는 구조로 풀었다 |
| 결과 | 스킬 13개, Gate 7개, Checklist 6개로 갱신(`05.WORKING_CONTEXT.md`, `HISTORY_DIGEST.md` 반영). "검수 대상 ZIP이 실제 배포본과 다르다"는 사실은 해시 대조로 직접 확인 후 근거 문서에 기록했고, 그에 기반한 P0 항목(단일 루트 복구, Adapter 신설 등)은 반영하지 않았다. |

## ADR-037. `ui-ux-design`에 기계적·획일적 결과 방지 검토 추가

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 배경 | 기존 `ui-ux-design`은 사용자 목표, 흐름, 상태, 반응형, 접근성, 구현 가능성을 충분히 다뤘지만, 결과물이 기계적으로 반복되거나 시각적 계층·문구·토큰 일관성이 약한 경우를 별도로 검토하지 않았다. 사용자는 이를 "AI 티"로 인식되는 결과를 줄이는 방향으로 보강해 달라고 요청했다. |
| 결정 | 기존 `ui-ux-design` 스킬, UI/UX Gate, UI/UX Checklist에 기술 중립적인 "기계적·획일적 결과 방지 검토"를 추가한다. 검토 범위는 토큰과 표면 규칙, 시각적 계층, 반복과 리듬, 장식 절제, 콘텐츠 현실성, 선택 근거다. 특정 미감·비대칭·기술 스택을 강제하지 않으며, 검토 또는 근거가 부족하면 일반 WARN으로 드러낸다. 핵심 행동을 식별할 수 없게 만드는 시각적 계층 문제는 FAIL이다. |
| 제외 | 특정 UI 라이브러리나 CSS 프레임워크 규칙을 공통 스킬에 추가하지 않고, 자동화 스크립트로 주관적 시각 품질을 판정하지 않는다. 프로젝트별 Stack Profile의 구현 규칙은 공통 스킬과 분리해 유지한다. |
| 이유 | 화면의 의도적 반복·비대칭·강한 표현은 서비스 목적에 따라 유효할 수 있으므로 금지 목록으로 처리하면 안 된다. 대신 사람이 근거를 남기며 검토하도록 해야 디자인 품질을 높이면서도 기술 중립성과 프로젝트별 표현의 자유를 유지할 수 있다. |
| 결과 | 화면 설계 산출물은 기존 UX·접근성·구현 가능성 기준에 더해, 결과물의 획일성·장식 과다·문구 현실성을 명시적으로 검토한다. Stack Profile 분리 원칙(ADR-036)은 그대로 유지한다. |

## ADR-038. PrimeVue + Tailwind Stack Profile의 구현 경계와 예외 기록 보강

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 배경 | ADR-037의 공통 검토 기준은 기술 중립적으로 유지해야 한다. 다만 PrimeVue + Tailwind CSS를 실제로 쓰는 프로젝트에서는 디자인 토큰을 어디에 연결하고, 표준 컴포넌트 대신 커스텀 구현을 언제 허용할지에 대한 구현 경계가 더 필요하다. |
| 결정 | `STACK_PROFILE_PRIMEVUE_TAILWIND.md`에 토큰·테마 연결, 커스텀 컴포넌트와 스타일 예외의 허용 조건·기록 항목, 구현 전·후 확인 항목을 추가한다. PrimeVue는 동작·상태·접근성이 필요한 표준 컴포넌트를, Tailwind는 레이아웃과 의미 기반 토큰 적용을 담당한다. |

| 결과 | PrimeVue + Tailwind를 활성화한 프로젝트는 공통 UI/UX 검토를 구현 단계까지 일관되게 이어갈 수 있다. 다른 스택에는 적용되지 않으며, Profile은 선택적으로만 활성화된다. |

## ADR-039. Git-first 공식 반영과 `AGENTS.md` 단일 진입점

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 배경 | ZIP을 배포 Source of Truth로 두던 규칙은 Git 저장소 중심 운영과 충돌했고, 기존 단수형 루트 에이전트 문서는 표준 자동 인식 파일명과 일치하지 않았다. |
| 결정 | Git 저장소를 배포·이력 Source of Truth로 한다. 작업 브랜치 push는 공유 진행 상태, `main`에 병합된 커밋만 공식 반영이다. 루트 에이전트 진입점은 `AGENTS.md` 하나로 표준화하고 기존 단수형 문서는 제거한다. `CLAUDE.md`는 보조 안내로 유지한다. 두 진입 문서는 자동 검증 범위에서 제외하며 변경 시 수동 검수한다. |
| 이유 | 작업 중인 변경과 공식 반영을 구분하면서, 도구 호환성이 높은 단일 진입점과 과도하지 않은 운영 기록을 유지한다. |
| 결과 | Report 완료 절차는 Git 기준으로 정리되고, ZIP 검증은 사용자가 export를 요청한 경우에만 선택적으로 수행한다. 과거 ZIP 관련 ADR·Report는 당시 결정의 역사 기록으로 보존한다. |

## ADR-040. `intent-to-implementation` 축소 반입과 보조 참조 문서 규칙 공식화

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 배경 | 외부 제공 스킬 패키지 `intent-to-implementation`은 "요청 접수→조사→요구사항 재구성→계약→계획→구현→검증→설명" 전 파이프라인을 자체 소유하는 독립형 미니 하네스였다. 그대로 반입하면 같은 단계 규칙이 두 곳에 생기고 `00.HARNESS_RULES.md §3` 바깥에 평행 우선순위가 생긴다(반입 검수 P-16). 또한 영어 본문, YAML frontmatter, 벤더 배포 파일(`agents/openai.yaml`, icon), 마크다운 링크 참조 등 하네스 표준과 어긋나는 형식 문제가 있었다(P-15, P-18). 한편 실사용 Report 10건 분석에서 이 스킬의 requirement-reconstruction이 잡았어야 할 실패(services→domain 같은 날 재작업, P-05)가 실제로 발생해 반입 근거는 실증됐다. |
| 결정 | (1) 기존 문서에 소유자가 없는 4개 가치 — 의도 라우팅, 요구사항 재구성(Confirmed/Inferred/Unresolved), 최소 해법 나침반, 변경 설명 형식 — 만 유지하고, 소유자가 있는 절차(작업 계약=`AGENTS.md`, 사전 조사=`CLAUDE.md §1`, 계획=`planning`, 검증=`verification-loop`)는 참조로 치환해 14번째 스킬로 반입한다. (2) 본문은 한국어 하네스 7섹션 표준으로 재작성하고 frontmatter·벤더 파일은 반입하지 않는다. (3) 참조 4종은 `references/` 하위 폴더 대신 스킬 폴더 바로 아래 `REFERENCE_*.md` 평면 구조로 두고, 이 구조를 `01.SKILL_TEMPLATE.md §2-1` "보조 참조 문서 규칙"으로 공식화한다(선례: `ui-ux-design`의 STACK_PROFILE 분리, ADR-036). |
| 이유 | 스킬은 하네스의 하위 모듈이라는 원칙(`00.HARNESS_RULES.md §2-3`)을 지키려면 파이프라인 소유권이 아니라 공백 4개만 가져와야 한다. 참조 문서를 평면 구조로 두면 새 폴더 규칙 없이 기존 선례와 `validate-references.mjs` 코드 span 검사를 그대로 활용할 수 있다. |
| 결과 | 활성 스킬 14개. 사용률 0% 스킬이 9개인 상태에서의 추가라는 우려(P-04)는 skill-stocktake 판정을 같은 작업에서 선행하는 것으로 처리했다 — 이 스킬은 발동 조건이 "모든 모호한 요청"이라 기존 0회 스킬들과 발동 빈도 특성이 다르다. 원저작 출처는 미확인 상태로 `_SOURCE_MAPPING.md §0`에 기록한다. |

| 상태 | Accepted |

| 이유 | 폴더 분리(`reports/project/`)안보다 변경 범위가 작고, 부착형 운영에서 두 이력의 최신 포인터를 각각 유지할 수 있는 최소 구조다. |
| 결과 | 하네스 저장소가 자신의 실사용 데이터를 받을 공식 경로가 생긴다. 이번 작업 자체가 첫 환류 사례다(챱챱 Report 10건 분석 → 하네스 수정). |

## ADR-042. `browser-qa` D등급 장기 보류 → 정식 스킬 승격

| 상태 | Accepted |

## ADR-043. 스택 한정 스킬 범주 신설과 `vue-ui-polish` 반입

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 배경 | `_PENDING_IMPORT_LIST.md §3`은 "특정 프론트엔드 스택 기준을 전역 규칙으로 오해할 수 있음"을 이유로 `frontend-patterns` 원본 전체를 X등급 제외했다. `vue-ui-polish`는 이름부터 Vue 3 고정이라 같은 사유에 걸린다(반입 검수 P-17). 기존 해법(ADR-036)은 스킬 본체를 기술 중립으로 두고 스택 정책만 Stack Profile로 분리하는 것이었지만, 이 스킬은 절차 전체가 Vue에 결합되어 분리할 기술 중립 본체가 남지 않는다. 한편 이 하네스는 프로젝트마다 따로 부착해 쓰고 프로젝트 간에 이관하지 않는 운영 방식이라(사용자 확인, 2026-08-03), 스택 한정 스킬이 다른 스택 프로젝트를 오염시킬 경로가 구조적으로 약하다. |
| 결정 | "스택 한정 스킬" 범주를 신설한다(`01.SKILL_TEMPLATE.md §2-2`). 조건: Harness Control Rule에 발동 스택을 명시하고, 해당 스택이 아닌 프로젝트에서는 스킬의 존재 자체를 무시한다고 적는다. 이 조건을 충족하는 `vue-ui-polish`를 16번째 스킬로 반입한다. MIT 파생 작업(Emil Kowalski, Skills for Design Engineers)이므로 `skills/vue-ui-polish/LICENSE`를 함께 반입하고 SKILL.md의 파생 고지 문장을 유지한다(P-19) — 하네스에 외부 LICENSE 파일이 들어오는 첫 사례다. 벤더 배포 파일(`agents/openai.yaml`, icon)과 frontmatter는 기존 결정(ADR-040)과 동일하게 제외한다. |
| 이유 | X등급 제외 사유의 본질은 "스택 기준의 전역 오해"이지 스택 기준 자체가 아니다. 발동 경계를 스킬이 스스로 선언하면 오해 경로가 차단되고, 실사용 근거(챱챱 Report 10건 중 8건이 UI/UX 작업, 터치 영역·색상 대비·reduced-motion 문제가 반복 등장)가 이 스킬의 references와 정확히 겹친다 — 실증 근거가 가장 강한 반입이다. |
| 결과 | 활성 스킬 16개. `_PENDING_IMPORT_LIST.md §3`의 `frontend-patterns` 행에 스택 한정 스킬 예외를 추기한다. 다른 스택 전용 스킬(React 등)도 같은 조건을 충족하면 이 범주로 반입할 수 있다. |

## ADR-044. 집행층 도입 — 규칙의 문서 의존을 기계 강제로 전환

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 배경 | 두 종류의 실증 근거가 쌓였다. (1) 실사용 Report 10건 분석에서 "규칙은 있는데 실행되지 않는" 불이행이 반복 확인됐다 — planning 발동 조건 충족 7건 중 0회, git-workflow 0회, Git 이력 기록 10/10 누락. 산문 규칙은 읽혀야만 작동하는데, 문서가 71개로 늘어나며 읽기 자체가 생략됐다. (2) 2026-08-02~03에 실제 유출 사고 2건 — 민감 검수 문서·외부 zip이 PUBLIC 저장소에 push되어 이력 재작성으로 제거했고, 로컬 에이전트 설정(`.claude/settings.json`)이 `git add -A`에 딸려 커밋됐다. 사람/에이전트의 주의에 의존하는 통제는 실측 준수율이 낮다. |
| 결정 | 규칙을 4가지 기계 장치로 변환한다. (1) **CI**: `.github/workflows/harness-ci.yml`이 push(main)/PR마다 검증 스크립트 7종을 강제 실행한다. (2) **시크릿 검사**: `scripts/validate-no-secrets.mjs` 신설 — 금지 파일 패턴(`.claude/`, zip, .env, 키 파일)과 알려진 토큰 패턴을 Git 추적 파일에서 검사하고 CI에 포함한다. (3) **브랜치 보호**: `main`에 required status check(validate)·force-push 금지·삭제 금지를 설정해 "main 병합만 공식 반영" 규칙을 저장소 설정으로 강제한다. (4) **PR 템플릿**: Report·GateGuard·검증 확인 항목을 `.github/pull_request_template.md`로 두어 PR마다 눈에 보이게 한다. 추가로 **2층 읽기 모델**(`03.CONTEXT_BUDGET.md §2-2-1`)을 도입해 상시 표면을 4개+α 문서로 압축하고, 나머지는 트리거 기반 로딩으로 강등한다. |
| 이유 | 이 하네스의 규칙층은 실증 사고 기반이라 걷어낼 수 없지만, 준수를 문서 읽기에 의존하는 한 같은 불이행이 반복된다. 현업 표준(CI·branch protection·PR 템플릿)은 잊어도 작동하는 장치이고, 기존 검증 스크립트가 순수 Node라 CI 전환 비용이 거의 없다. 읽기 표면 압축은 "문서가 많을수록 준수율이 떨어진다"는 실측 역학에 대한 직접 대응이다. |
| 결과 | 검증 스크립트 8종(export 전용 validate-package 포함), CI 상시 7종. 하네스 수정이 main에 들어가려면 사람이 기억하지 않아도 검증을 통과해야 한다. 문서 규칙과 기계 장치의 역할 분담: 문서는 판단 기준을 소유하고, CI/보호 설정은 이행을 강제한다. |

## ADR-045. `vue-ui-polish` 개정 반입과 스킬 보조 스크립트 규칙 — 하네스 동결의 마지막 예외

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 배경 | 사용자가 `vue-ui-polish`의 대폭 확장 개정본을 제공했다(참조 3→11종, 정적 감사 스크립트 신규, 원저작 3인으로 확대 — Emil Kowalski + Hallmark 계열 + Taste Skill/Leonxlnx). 기존 반입본은 실전에서 한 번도 발동되지 않은 상태라, 첫 사용 전에 상위 호환본으로 교체하는 비용이 지금이 가장 낮다. 단, 하네스 동결 선언(2026-08-03) 이후의 비사고 기반 수정이라는 충돌이 있다. |
| 결정 | (1) 기존 스킬을 개정본으로 **교체**한다(활성 스킬 16개 불변, 신규 추가 아님). 실행 모드 5종(build/audit/polish/redesign/study), P0~P6 품질 사다리, anti-AI 패턴(필수 실패/맥락 경고 분리), 외부 계약 보존 규칙을 하네스 7섹션으로 재구성. (2) `ui-ux-design`과의 소유권 경계를 명시한다 — 기술 중립 화면 설계는 `ui-ux-design` 소유, 이 스킬의 설계성 절차는 Vue 구현 맥락 한정. (3) 스킬 전용 보조 스크립트 규칙을 신설한다(`01.SKILL_TEMPLATE.md §2-1`): `skills/{name}/scripts/` 허용, 순수 Node, 후보 제시 전용(Gate 판정·CI 차단 대체 금지). (4) 저작권자 3인이 된 LICENSE로 교체하고 파생 고지를 갱신한다. (5) frontmatter·벤더 파일(`agents/openai.yaml`, icon)은 기존 결정(ADR-040/043)대로 제외한다. |
| 이유 | 개정본의 품질이 실증 문제를 정조준한다 — 모드 경계("봐줘"는 수정 권한이 아님)는 i2i 의도 라우팅과 동일 철학이고, P0~P6 사다리는 판단 우선순위(기능>이해>접근성>일관성>반응형>시각>모션)를 검사 순서로 강제하며, 정적 감사 스크립트는 집행층 방향(실행 장치>산문)과 일치한다. 동결 예외는 "미사용 자산의 사용 전 교체"라는 조건에서만 정당화되며, **이 반입을 동결의 마지막 예외로 한다** — 이후 하네스 수정은 실전 사고 기반만 허용한다. |

| 항목 | 내용 |
|---|---|
| 상태 | 로컬 구현·검증 대상, 미커밋·미병합 |
