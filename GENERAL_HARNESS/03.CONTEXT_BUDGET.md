# 03. CONTEXT BUDGET

> 한국어 별칭: 컨텍스트 예산 규칙  
> 목적: AI Agent가 모든 문서를 무작정 읽지 않도록 작업 규모별 컨텍스트 사용량을 제한한다.  

---

## 1. 왜 필요한가

하네스 문서가 많아지면 모든 파일을 매번 읽는 방식은 비효율적이다.

문제:

- 토큰 낭비가 커진다.
- 중요한 문서와 덜 중요한 문서가 섞인다.
- AI가 오래된 문맥과 현재 요청을 혼동할 수 있다.
- 간단한 작업도 과하게 분석하게 된다.

따라서 작업 전에 **필요한 문서만 고르는 규칙**이 필요하다.

---

## 2. 작업 규모 분류

프로젝트 어댑터가 있는 경우 context는 진입 표면에 포함하고 제품 문서 본문은 선택한 작업 route로 제한한다. 전체 문서 경로 검사를 전체 본문 로딩으로 해석하지 않는다. [Project Adapter](PROJECT_ADAPTER.md)가 경로·버전 계약을 소유한다.

| 규모 | 설명 | 읽을 문서 범위 |
|---|---|---|
| S | 단순 질문, 오타 수정, 작은 설명 | 관련 파일 1~2개 |
| M | 문서 일부 작성, API 일부 설계, 체크리스트 작성 | 상위 규칙 + 관련 스킬 + 관련 Gate |
| L | 하네스 구조 변경, 여러 문서 연결, 스킬 추가 | 상위 규칙 + Skill Index + 관련 문서 전체 |
| XL | 전체 구조 개편, 대규모 반입, 장기 작업 | Working Context + ADR + 전체 핵심 문서 |


### 2-1. Quick Ref 우선 로딩 원칙

| 작업 규모 | 우선 로딩 | 00 전체 로딩 조건 |
|---|---|---|
| S | 관련 파일 + `00.QUICK_REF.md` (충돌·위험 판단 필요 시) | 원칙적으로 생략 |
| M | `00.QUICK_REF.md` + 관련 Skill/Gate/Checklist | 충돌 판단, 위험 작업, 하네스 규칙 해석이 필요할 때 |
| L | `00.QUICK_REF.md` + 관련 핵심 문서 | 구조 변경 또는 규칙 변경이 포함될 때 |
| XL | `00.HARNESS_RULES.md` 전체 + 관련 핵심 문서 | 항상 확인 |

`00.QUICK_REF.md`는 일반 작업의 런타임 진입점이고, `00.HARNESS_RULES.md`는 원천 규칙이다.


### 2-2. 실행 환경별 보정 규칙

작업 규모(S/M/L/XL)가 1차 기준이고, 실행 환경은 읽기 순서를 보정하는 2차 기준이다.

| 실행 환경 | 읽기 보정 |
|---|---|
| 로컬 파일 접근 가능 Agent | 실제 파일 목록과 수정 대상 파일을 먼저 확인한 뒤 필요한 규칙 문서만 추가로 읽는다. |
| 도구 호출 기반 Agent | `00.QUICK_REF.md`와 작업 대상 문서의 존재 여부를 먼저 확인하고, 필요한 Gate/Skill만 좁혀 읽는다. |
| 대화형 설명 중심 Agent | 파일 수정 없이 설명만 하는 경우 전체 하네스 로딩을 피하고, 충돌·위험 판단이 필요할 때만 Quick Ref를 읽는다. |
| 하네스 자체 수정 Agent | 실행 환경과 관계없이 `00.HARNESS_RULES.md`, `00.QUICK_REF.md`, `03.CONTEXT_BUDGET.md`, `04.GATEGUARD.md`, `08.QUALITY_GATE.md`, `09.AGENT_WORKFLOW.md`를 우선 확인한다. |

실행 환경별 보정은 특정 도구명을 고정하기 위한 규칙이 아니라, 같은 작업 규모라도 실제 접근 권한과 수정 위험이 다를 수 있음을 반영하기 위한 규칙이다.

### 2-2-1. 상시 표면과 심층 문서 (2층 읽기 모델)

조건부 심층 문서: UI 기능·데이터·세션 변경 때만 `checklists/ui-ux-checklist.md §1-3`을 읽는다. 별도 AI Runtime 연동 계약/구현 때만 [AI Runtime Handoff](AI_RUNTIME_HANDOFF_TEMPLATE.md)와 `checklists/ai-runtime-integration-checklist.md`를 읽는다. 일반 문서·단순 시각 수정·단순 모델 사용은 이 추가 로딩의 트리거가 아니다.

실사용 검수(2026-08-02)에서 확인된 사실: 문서가 많아질수록 개별 규칙의 준수율이 떨어진다 — 규칙이 있어도 읽지 않으면 발동하지 않는다(planning 0/7회, git-workflow 0회). 이를 반영해 에이전트가 읽는 문서를 2층으로 나눈다(ADR-044).

**1층 — 상시 표면(모든 작업에서 기본 로딩, 4개 + α)**

| 문서 | 역할 |
|---|---|
| `AGENTS.md`(저장소 루트) | 진입 지도 |
| `00.QUICK_REF.md` | 우선순위·위험 판정·PASS/WARN/FAIL 실행 요약 |
| `04.GATEGUARD.md` §6-1 | 위험 유형별 해제 조건(수정 작업이 있을 때) |
| 이번 작업의 발동 스킬 1~2개 | `02.SKILL_INDEX.md §4`로 선택 |

**2층 — 심층 문서(명시된 트리거에서만 로딩)**

| 트리거 | 읽는 문서 |
|---|---|
| 규칙 충돌·해석 필요 | `00.HARNESS_RULES.md` |
| 하네스 자체 수정 | §2-2 "하네스 자체 수정 Agent" 행의 목록 |
| Gate 통과가 필요한 산출물 | 해당 `gates/*.md`, `checklists/*.md` |
| 버전·API·설정 근거 불확실 | `skills/documentation-lookup/SKILL.md` |
| 업무 규칙·권한·상태 변경의 검증 설계 부족 | `skills/test-design/SKILL.md` |
| 코드/diff 검토 요청 또는 구체적 구조 우려 | `skills/code-review/SKILL.md`; 기존 테스트 검수 때만 해당 REFERENCE_TEST_REVIEW 참조 |
| 흐름 문서 생성·갱신 | `skills/universal-flow-document/SKILL.md`; 작성 시 FORMAT/AUTHORING, 출처 검토 시 PROVENANCE 참조 |
| 스킬의 실제 행동 준수 유지보수 평가 | `skills/skill-stocktake/REFERENCE_BEHAVIOR_EVAL.md` |
| Report 작성 시점 | `06.REPORT_TEMPLATE.md` |
| 이전 작업 이어받기 | `reports/_LATEST.md`, `05.WORKING_CONTEXT.md` |
| 반입·구조 결정 이력 추적 | `_SOURCE_MAPPING.md`, `_PENDING_IMPORT_LIST.md`, `10.ADR.md` |

1층만 읽고 시작할 수 있는 작업(S/M 대부분)은 1층만으로 시작한다. 2층 문서를 "혹시 몰라서" 미리 읽는 것은 §8 기준 WARN이다. 반대로 트리거가 발생했는데 해당 2층 문서를 읽지 않는 것은 FAIL이다.

### 2-3. 혼합 운영 First Reading 예시

아래 표는 특정 제품명에 종속된 규칙이 아니라, Claude처럼 문서/SRS 판단에 강한 Agent와 Codex처럼 로컬 파일 접근·검증·이어받기에 강한 Agent를 함께 사용할 때의 최소 읽기 경로 예시다. 이 표는 §2-2의 "로컬 파일 접근 가능 Agent"·"도구 호출 기반 Agent" 범주를 혼합 운영 상황에 맞게 구체화한 것이며, §2-2를 대체하지 않는다.

| 운영 형태 | 우선 읽기 | 보조 읽기 | 주의 |
|---|---|---|---|
| Claude 중심 문서/SRS 판단 | `00.QUICK_REF.md`, 작업 대상 문서 | `gates/document-gate.md`, `checklists/srs-checklist.md`, 필요 시 `03.CONTEXT_BUDGET.md` | 원본/추출본/요약본 관계가 있으면 `checklists/srs-checklist.md §0-1`을 확인한다. |
| Codex 중심 로컬 실행/검증 | 실제 파일 목록, 수정 대상 파일, `00.QUICK_REF.md`, `04.GATEGUARD.md` | 관련 `skills/*/SKILL.md`, 관련 Gate, Handoff Note가 있으면 `05.WORKING_CONTEXT.md` | 파일 수정·삭제·대량 변경 전에는 GateGuard 위험도를 먼저 확인한다. |
| Claude → Codex 인계 | Claude가 읽은 문서와 판단 근거 | Codex가 수정할 파일, 검증 명령, 적용 Gate | Handoff Note에 `읽은 문서`와 `다음에 먼저 읽을 문서`를 반드시 남긴다. |
| Codex → Claude 리뷰 | 수정 파일 목록, 검증 결과, Report | 관련 Gate/Checklist, 미해결 WARN/FAIL | 구현 완료 추정이 아니라 검증 증거 기준으로 리뷰한다. |
| 하네스 자체 수정(혼합 운영 중이라도) | `00.HARNESS_RULES.md`, `00.QUICK_REF.md`, `03.CONTEXT_BUDGET.md`, `04.GATEGUARD.md`, `08.QUALITY_GATE.md`, `09.AGENT_WORKFLOW.md` | 위 4개 운영 형태의 보조 읽기 문서 | 실행 환경이나 운영 형태와 관계없이 §2-2의 "하네스 자체 수정 Agent" 행을 우선 따른다. |

역할별 First Reading은 작업 규모 규칙을 대체하지 않는다. 작업이 L/XL이면 역할과 관계없이 상위 규칙과 관련 핵심 문서를 추가로 확인한다.

## 4-1. 중복 읽기 방지 원칙

같은 파일을 다시 확인해야 할 때는 먼저 변경 여부(diff 또는 이전 확인 시점 이후 수정 여부)를 확인하고, 변경이 없으면 이전 확인 내용을 근거로 재사용한다. 전체를 다시 읽지 않는다.

다만 다음 경우는 이 원칙에서 제외하며, 항상 실제로 다시 읽는다.

- 수정 직후 "제대로 반영됐는지" 검증하는 경우(`skills/verification-loop/SKILL.md`의 목적과 겹치므로 줄이지 않는다)
- 위험 작업(구조/DB/보안/결제/파일 손상 가능) 판정 직전
- 같은 대화·세션이 길어져 이전 확인 내용이 요약되거나 맥락에서 벗어난 경우

보조 문서는 매번 읽지 않는다. 현재 작업의 판단 근거에 직접 연결될 때만 읽는다.

---

## 4-2. 최신성 충돌 Stop Condition

다음 경우 새 작업(신규 구현, 문서 대량 수정, 스킬 추가)을 시작하지 않는다.

- `reports/_LATEST.md`와 `05.WORKING_CONTEXT.md`가 서로 다른 최신 Report를 가리키는 경우
- `02.SKILL_INDEX.md`의 Active 스킬 수와 `05.WORKING_CONTEXT.md`의 현재 상태 표가 다른 경우
- 문서 내부에 적힌 참조 경로(파일/스킬/Report)가 실제 파일 구조와 맞지 않는 경우

이 경우 구조 WARN으로 기록하고, 최신 기준을 먼저 동기화한 뒤 원래 작업을 재개한다. 동기화 여부는 `skills/report-consistency/SKILL.md`, 참조 경로 확인은 `scripts/validate-references.mjs`로 확인한다.

## 5. Report 읽기 순서

`reports/*.md`가 여러 개 있으면 다음 순서로 읽는다.

1. `reports/_LATEST.md`를 먼저 확인한다.
2. `_LATEST.md`가 가리키는 최신 판단 기준 Report를 읽는다.
3. `05.WORKING_CONTEXT.md`의 현재 상태와 최신 Report가 일치하는지 확인한다.
4. 오래된 Report는 변경 근거와 증거로만 사용한다. **단, `reports/archive/HISTORY_DIGEST.md`의 삭제 이벤트(`PURGE_EVENT` 블록)에 있는 파일은 원본이 삭제된 상태다 — 그 경우 digest의 한 줄 요약이 유일한 근거이며, 원본을 직접 열어 상세를 재현할 수 없다(외부 검수 M-08/X-09, ADR-031/034).**

날짜가 같은 Report가 여러 개 있으면 날짜만으로 최신성을 판단하지 않는다. 이 경우 `_LATEST.md` 또는 superseded note를 따른다.

| 상황 | 읽기 기준 |
|---|---|
| 최신 Report와 오래된 Report의 다음 작업이 다름 | 최신 Report 우선 |
| 오래된 Report에 superseded 표시가 있음 | 증거로만 확인 |
| 실패/중단 이력이 최신 Report에 남아 있음 | 새 작업 전 재판정 |
| 특정 패치의 근거를 추적해야 함 | 해당 과거 Report를 직접 확인. **원본이 삭제 이벤트(`PURGE_EVENT`)에 포함되어 있으면 직접 확인 불가 — digest 요약으로 대체** |

## 6. 읽지 않아도 되는 경우

다음 경우에는 전체 하네스를 읽지 않는다.

- 단순 용어 설명
- 단일 코드 조각 설명
- 이미 범위가 확정된 문서 한 개 수정
- 사용자가 특정 파일 하나만 검수 요청
- 과거 산출물과 연결되지 않는 일반 질문

## 7. 장기 작업 요약 규칙

장기 작업에서 이전 리포트가 많아지면 전체를 매번 읽지 않는다.

| 상황 | 처리 |
|---|---|
| Report가 5개 이하 | 필요한 Report만 직접 확인 |
| Report가 6개 이상 | `05.WORKING_CONTEXT.md`에 핵심 요약을 남기고 Report는 증거로 보관 |
| 오래된 Working Context와 최신 요청 충돌 | 최신 요청 우선, 단 안전 규칙은 유지 |
| 미해결 FAIL/WARN 존재 | 새 작업 전 상태 재판정 |

Working Context는 전체 기록 저장소가 아니라 **현재 상태 요약본**이다.


`05.WORKING_CONTEXT.md`는 이미 신규 프로젝트 템플릿으로 전환되었다(`10.ADR.md` ADR-027, 이전의 "분리 보류" 결정은 대체됨). 일반 작업에서는 필요한 최신 상태와 `_LATEST.md` 포인터만 확인하고, Working Context 형식 자체를 바꾸는 작업에서만 전체 절차 설명을 확인한다.

## 8. 컨텍스트 예산 판정

| 판정 | 기준 |
|---|---|
| PASS | 필요한 문서만 선택했고, 선택 이유가 명확함 |
| WARN | 읽은 문서가 많지만 작업 성격상 허용 가능함 |
| FAIL | 전체 파일을 무조건 읽거나, 핵심 문서를 빠뜨림 |

---

## 9. 작업 전 질문

Agent는 작업 전에 내부적으로 다음을 판단한다.

```txt
1. 이 작업은 S/M/L/XL 중 어디에 해당하는가?
2. 반드시 읽어야 하는 문서는 무엇인가?
3. 읽으면 오히려 방해되는 문서는 무엇인가?
4. 산출물이 어떤 Gate를 통과해야 하는가?
5. 결과를 Report 또는 Working Context에 남겨야 하는가?
6. 이전 FAIL/WARN 또는 중단 이력이 현재 작업에 영향을 주는가?
```

## 10. Report 보존 규칙

| 구분 | 처리 |
|---|---|
| 최신 Report | 다음 작업 판단 기준으로 우선 확인 |
| Superseded Report | 과거 의사결정 근거와 변경 증거로만 보관 |
| 오래된 Report | Working Context에 요약되었다면 직접 로딩 우선순위를 낮춤 |
| 삭제 | 사용자가 명시하지 않는 한 삭제하지 않음 |

Report가 많아지면 오래된 Report를 삭제하기보다 Working Context에 핵심만 요약하고, 오래된 Report는 증거로 보존한다.
