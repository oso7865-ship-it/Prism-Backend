## 2. FAIL 기준

- 제출 범위와 실제 구현이 다름
- 결제/인증/주문 핵심 흐름이 깨짐
- DB와 API 명세가 서로 다름
- 더미데이터/보류 기능을 실제 구현처럼 표시함
- 테스트 증거 없이(N/A 사유도 없이) 릴리즈함
- 롤백 방법이 없는 채로 되돌리기 어려운 변경(DB 마이그레이션 등)을 배포함
- DB 변경이 있는데 백업/복구 절차를 확인하지 않음
- 적용 범위가 "운영 배포용"인데 §1-1 항목(비밀값 분리/모니터링/로그/임계값/책임자/관찰기간) 없이 배포함

## 결과 요약

> 이 표는 **이 Checklist 자체의 판정**이다. 산출물 전체의 최종 판정은 `08.QUALITY_GATE.md §7-2`의 전역 공식(`maxSeverity(Verification, 적용 Gate 전부, 적용 Checklist 전부)`)을 따른다 — 이 표가 PASS여도 같은 산출물의 Gate나 Verification이 WARN/FAIL이면 전체 최종 판정은 그 WARN/FAIL이다(외부 검수 M-05/G-06).

| 판정 | 기준 |
|---|---|
| PASS | 릴리즈 범위, DB, API, 인증/권한, 결제/주문 흐름, 빌드, 보류 표시, 테스트 증거, 롤백 가능성, 배포 후 점검 계획이 모두 확인됨(해당 없는 항목은 N/A와 사유로 대체) |
| 일반 WARN | README, 설명, 더미데이터 표기 등 보조 문서가 일부 부족하지만 핵심 흐름은 안전함 |
| 구조 WARN | 문서 연결, 산출물 소유권, 번호 체계, 인계 기준이 일부 모호해 추가 근거 확인 또는 사용자 확인이 필요함 |
| 위험 WARN | 인증/권한/결제/DB/빌드 중 일부가 불명확해 사용자 확인 또는 추가 근거 전 진행 금지 |
| FAIL | 릴리즈 범위와 실제 구현 불일치, 핵심 흐름 깨짐, 빌드 실패, 보류 기능을 실제 구현처럼 표시, 테스트 증거 없음, 되돌리기 어려운 변경에 롤백 방법 없음, DB 변경에 백업/복구 미확인, 적용 범위가 "운영 배포용"인데 §1-1(비밀값 분리/모니터링/로그/임계값/책임자/관찰기간) 없이 배포함 |

Checklist 판정 칸에는 `PASS`, `WARN`, `FAIL` 중 하나를 쓰고, WARN인 경우 Report에 `일반 WARN`, `구조 WARN`, `위험 WARN` 중 하나를 함께 적는다.

Checklist 결과는 `06.REPORT_TEMPLATE.md`의 Checklist 결과 섹션에 옮긴다.
