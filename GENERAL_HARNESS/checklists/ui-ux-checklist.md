## 1-3. 기능·데이터·세션 검증 — 관련 기능 변경 시 적용

단순 색상·간격·문구 수정에는 자동 발동하지 않는다. 기능 설계 단계에서는 계약과 예상 결과를, 구현 단계에서는 재현 절차와 관측 결과를 기록한다. 설계 검토 PASS를 실제 연동 PASS로 사용하지 않는다. 해당 없는 기능은 사유가 있는 N/A만 허용한다.

| 항목 | 결과(PASS/FAIL/N/A) | 근거·미해결 항목 |
|---|---|---|
| UI-F01: 업무 데이터의 API/store/fallback 경로를 확인하고, 운영 화면에서 실패를 더미 데이터나 가짜 성공으로 감추지 않는가? | ☐ | 대상 화면·데이터 출처·실패 응답 시 표시 |
| UI-F02: 제품 상수와 테스트 전용 fixture/mock을 업무 더미와 구분하고, 공유 데이터 변경 시 다른 소비 화면의 영향을 확인했는가? | ☐ | 실행 환경·참조 화면·mock 격리 근거 |
| UI-F03: 서버의 계약상 성공을 확인한 후 저장 완료를 표시하는가? 낙관적 UI는 대기 상태와 실패 시 복구가 있으며 최종 저장으로 오인시키지 않는가? | ☐ | 요청·응답·화면 상태 전이 |
| UI-F04: API 부재·미확정은 준비 중/사용 불가로 표시하고, 로딩·빈 결과·오류·재시도를 구분하는가? | ☐ | 미지원 기능·후속 담당자·각 상태 근거 |
| UI-F05: 새로고침 세션 복원·만료·권한 거부를 프로젝트 인증 계약대로 처리하고 편의를 위해 인증정보 저장 위치나 권한 검사를 우회하지 않는가? | ☐ | 인증 계약·복원/만료/거부 시나리오 |
| UI-F06: 처리 중 표시와 중복 제출 방지가 있으며, 타임아웃 후 재시도는 서버의 멱등성 계약을 확인하는가? | ☐ | 연속 클릭·지연·재시도 결과 |
| UI-F07: 실패 시 보존 가능한 입력을 유지하고 민감정보는 계약에 따라 지우며, 복구 경로를 안내하는가? | ☐ | 보존/삭제 대상·복구 결과 |
| UI-F08: 화면 이동·뒤로가기·취소 후 늦은 응답이 새 상태를 덮지 않으며, 실시간 연결이 있으면 끊김·재연결·중복 이벤트를 처리하는가? | ☐ | 응답 순서·취소·재연결 재현 결과 |

각 근거에는 대상 버전·검증 환경·예상/관측 결과·증거 위치를 남긴다. 실제 API, mock, 설계 검토를 구분하고 미확인 항목·담당자·다음 확인 방법을 Report에 기록한다. 항목별 미확인은 결과 칸을 비워 두고 근거에 표시하며 Checklist 전체를 WARN으로 집계한다(확정 위반 또는 verification-loop FAIL이 있으면 FAIL 우선).

기능 검증 기록 예: 저장 클릭 → 실패 응답 → 오류 안내 유지 → 재조회 시 기존 값 유지. 실제 응답을 관측하지 못했다면 '미관측', mock이면 'mock'으로 적는다. `skills/browser-qa/SKILL.md`의 도구·뷰포트·관측 기록에 연결하며 UI-F 항목을 복제하지 않는다. 단순 시각 수정에는 이 기능 검증을 강제하지 않는다.

## 2. FAIL 기준

§1-3 적용 항목의 위반도 FAIL이다. 미검증은 PASS나 N/A로 바꾸지 않고 미확인 근거와 WARN 유형을 기록한다. 실행 전제 조건 미비로 테스트를 건너뛴 경우는 verification-loop의 FAIL 기준을 따른다.

- 사용자 목표 또는 핵심 행동을 판단할 수 없음
- 필요한 API·데이터가 없는데 확정 디자인으로 처리함
- Loading/Error 상태가 전혀 없음
- 모바일에서 핵심 기능 수행이 불가능함
- 키보드 사용자가 핵심 기능을 수행할 수 없음
- Stack Profile이 활성화되어 있는데 그 금지 규칙을 위반함

## 결과 요약

> 이 표는 **이 Checklist 자체의 판정**이다. 산출물 전체의 최종 판정은 `08.QUALITY_GATE.md §7-2`의 전역 공식(`maxSeverity(Verification, 적용 Gate 전부, 적용 Checklist 전부)`)을 따른다 — 이 표가 PASS여도 같은 산출물의 Gate나 Verification이 WARN/FAIL이면 전체 최종 판정은 그 WARN/FAIL이다.

| 판정 | 기준 |
|---|---|
| PASS | 필수 항목과 §1-2의 검토 항목이 모두 확인되었고, Stack Profile이 활성화된 경우 §1-1, 기능 변경 시 §1-3도 충족됨 |
| 일반 WARN | 설명이 일부 부족하거나 §1-2의 검토·근거가 불완전하지만 핵심 흐름·상태·접근성 판단에는 지장 없음 |
| 구조 WARN | 문서 연결, 산출물 소유권, 번호 체계, 인계 기준이 일부 모호해 추가 근거 확인 또는 사용자 확인이 필요함 |
| 위험 WARN | 개인정보·권한·결제 관련 화면에서 접근성 또는 보안 관련 정보가 불명확해 사용자 확인 또는 추가 근거가 필요함 |
| FAIL | §2 FAIL 기준 중 하나라도 해당함 |

Checklist 판정 칸에는 `PASS`, `WARN`, `FAIL` 중 하나를 쓰고, WARN인 경우 Report에 `일반 WARN`, `구조 WARN`, `위험 WARN` 중 하나를 함께 적는다.

Checklist 결과는 `06.REPORT_TEMPLATE.md`의 Checklist 결과 섹션에 옮긴다.
