# 00. HARNESS RULES

> 한국어 별칭: 일반 하네스 최상위 규칙  
> 목적: 이 문서는 `GENERAL_HARNESS`의 최상위 규칙이다. 모든 문서, 스킬, 게이트, 체크리스트, 리포트는 이 문서를 기준으로 작성한다.  

---

## 1. 하네스의 역할

프로젝트별 제품 기준은 선택적 PROJECT_HARNESS 어댑터로 연결한다. 공통 하네스는 작업 통제를, 프로젝트 문서는 제품 계약을 소유한다. 어댑터는 아래 충돌 우선순위를 변경하지 않는다. 상세 계약은 [Project Adapter](PROJECT_ADAPTER.md)를 따른다.

이 하네스는 특정 프로젝트 하나에 종속되지 않는 **일반 AI 작업 하네스**다.

일반 작업에서는 이 문서 전체를 매번 읽지 않고 `00.QUICK_REF.md`를 우선 확인한다. 이 문서는 구조 변경, 충돌 판단, 하네스 자체 수정이 필요할 때 원천 규칙으로 읽는다.

목표는 다음과 같다.

| 목표 | 설명 |
|---|---|
| 규칙성 | 모든 산출물이 같은 기본 구조를 따른다. |
| 일관성 | 용어, 판단 기준, 작업 순서가 서로 충돌하지 않는다. |
| 통일성 | 스킬, 게이트, 체크리스트, 리포트가 같은 흐름으로 연결된다. |
| 검증 가능성 | 자동 검증 가능한 것과 사람/AI 리뷰가 필요한 것을 분리한다. |
| 유지보수성 | 스킬이나 문서가 늘어나도 구조가 무너지지 않는다. |
| 안전성 | 위험 작업은 근거와 검증 없이 진행하지 않는다. |

## 2. 기본 원칙

### 2-1. 문서 우선, 자동화 보조

현재 단계의 적정 비율은 다음과 같다.

```txt
문서 규칙 60%
수동 검수 25%
최소 자동화 15%
```

자동화는 처음부터 모든 것을 막는 도구가 아니라, 반복 실수와 구조 누락을 줄이는 보조 장치로 사용한다.

### 2-2. 원본 직접 복제 금지

외부 참고자료를 가져올 때는 다음 원칙을 따른다.

| 허용 | 금지 |
|---|---|
| 개념, 구조, 판단 기준 재작성 | 원본 전체 무비판 복사 |
| 필요한 섹션만 축소 반입 | 대규모 Agent/Command/Hook 생태계 통째 반입 |
| 일반 하네스에 맞는 중립 표현으로 변환 | 특정 프로젝트/스택 전용 표현을 전역 규칙처럼 고정 |
| 출처/반입 이유 기록 | 왜 가져왔는지 모르는 파일 추가 |

### 2-3. 하네스와 스킬의 상하 관계

스킬은 하네스의 하위 모듈이다.

| 규칙 | 설명 |
|---|---|
| 하네스 우선 | `00.HARNESS_RULES.md`, `04.GATEGUARD.md`, `07.SECURITY_BASELINE.md`, `08.QUALITY_GATE.md`는 모든 스킬보다 우선한다. |
| 스킬 중단 | 스킬 절차가 상위 하네스 규칙과 충돌하면 스킬 실행을 중단한다. |
| 안전 규칙 불가침 | 사용자 요청이나 스킬 절차로도 보안, 데이터 손상, 파일 삭제 방지 규칙을 덮어쓸 수 없다. |
| 스킬 확장 제한 | 새 스킬은 기존 스킬과 Gate를 확인한 뒤에만 추가한다. |


### 2-4. Git 공식 반영 정책

Git 저장소가 배포와 이력의 Source of Truth다.

| 상태 | 의미 |
|---|---|
| 작업 브랜치의 로컬 커밋 | 개인 작업 이력 |
| 작업 브랜치 push | 다른 사람이 확인할 수 있는 공유 진행 상태 |
| 프로젝트가 명시한 공식 반영 기준 브랜치에 병합된 커밋 | 해당 저장소의 공식 반영. 배포·실제 연동 확인과는 별도 |

- 기능/수정 작업은 작업 브랜치에서 수행한다. 공식 반영 기준은 프로젝트 루트 harness.config.json의 git.remote와 git.integrationBranch가 소유한다. 이 HARNESS 저장소는 origin/main을 사용한다.
- 다른 프로젝트에 부착할 때 기준 브랜치를 명시적으로 정한다. 설정이 없으면 main 또는 dev를 추측하지 않고 공식 반영 여부를 미확인으로 남긴다. 원격 기본 브랜치·현재 작업 브랜치는 자동 대체값이 아니다. 설정은 운영 의도를 나타내며 실제 원격 존재·병합을 증명하지 않는다.
- 구현·로컬 검증·병합·배포·실제 연동 상태는 서로 승격시키지 않는다. 상태별 증거와 Git 사건 후 동기화는 `06.REPORT_TEMPLATE.md §5-1`을 따른다.
- 버전·결정·검증의 상세는 커밋, `10.ADR.md`, `reports/*.md`, Working Context에 기록한다.
- `scripts/validate-package.mjs`와 ZIP은 기본 절차가 아니다. 사용자가 별도 export 산출물을 요청한 경우에만 선택적으로 사용한다.

## 3. 충돌 해결 우선순위

규칙, 사용자 요청, 이전 문서, 스킬이 충돌하면 아래 순서로 판단한다.

| 우선순위 | 기준 | 처리 |
|---:|---|---|
| 1 | 안전/보안/데이터 손상/파일 삭제 방지 규칙 | 절대 우선. 충돌 시 작업 중단 또는 사용자 확인 |
| 2 | 사용자의 최신 명시 요청 | 안전 규칙을 침해하지 않는 범위에서 우선 |
| 3 | `00.HARNESS_RULES.md` | 전역 판단 기준 |
| 4 | 현재 작업 계약과 `04.GATEGUARD.md` 결과 | 이번 작업의 범위와 위험도 기준 |
| 5 | 관련 Gate와 Checklist | 산출물별 품질 기준 |
| 6 | 관련 `skills/*/SKILL.md` | 작업 유형별 절차 |
| 7 | `05.WORKING_CONTEXT.md`, 이전 Report, 오래된 결정 | 최신 요청과 충돌하지 않는 범위에서 참고 |

오래된 Working Context나 이전 Report가 최신 사용자 요청과 충돌하면 최신 요청을 우선한다. 단, 안전/보안/데이터 손상 방지 규칙은 최신 요청으로도 덮어쓰지 않는다.

## 4. 공통 고정 용어

| 용어 | 의미 |
|---|---|
| Harness | AI 작업을 제어하는 전역 규칙·스킬·게이트·리포트 체계 |
| Skill | 특정 작업 유형에서 사용할 절차화된 작업 능력 |
| Gate | 산출물이 다음 단계로 넘어가도 되는지 판정하는 기준 |
| Checklist | 사람이 직접 확인해야 하는 검수 항목 |
| Report | 작업 결과, 검증 증거, 미해결 항목을 남기는 문서 |
| Working Context | 현재 작업 상태, 결정사항, 다음 작업 큐를 요약하는 문서 |
| ADR | 중요한 의사결정을 남기는 기록 문서 |
| Memory | 장기 기억 또는 프로젝트별 누적 지식. 현재 일반 하네스의 필수 문서가 아니며 프로젝트별 확장으로만 둔다. |
| Lessons Learned | 반복 실수와 개선 교훈. 현재 일반 하네스의 필수 문서가 아니며, 필요 시 Report/Working Context에 요약 후 프로젝트별 확장으로 승격한다. |
| PASS | 통과, 다음 단계 진행 가능 |
| WARN | 진행 가능 여부를 위험도에 따라 다시 판단해야 함 |
| FAIL | 수정 전까지 다음 단계 진행 금지 |

세부 PASS/WARN/FAIL 의미와 WARN 분기 기준의 소유 문서는 `08.QUALITY_GATE.md`다. 이 문서는 현재 작업에서 필요한 실행 요약만 둔다.

## 4-1. Memory 승격 경로

Memory와 Lessons Learned는 실수를 그냥 쌓아두는 목록이 아니다. 원본 기록을 계속 누적하면 `05.WORKING_CONTEXT.md`처럼 끝없이 길어지는 문제가 반복되므로, 아래 경로를 거친 것만 Memory에 압축된 형태로 남는다.

```text
실수/에러 발생
  → Report에 상세 기록 (1회성, 이 시점에서는 Memory에 올리지 않는다)
  → 같은 유형이 2회 이상 반복되면 Lessons Learned 후보로 표시
  → 사용자 확인
  → Memory에 1~2줄로 압축해 등록
  → 위험 작업과 관련된 실수라면 04.GATEGUARD.md §11 금지 패턴으로도 승격 검토
```

Memory에 등록하는 최소 형식은 다음과 같다.

```md
- [압축된 교훈 1줄]: 원인 요약 / 재발 방지를 위해 지금 적용 중인 규칙(문서·조항) / 근거 Report: `reports/...`
```

Memory는 원본 사건 기록이 아니라 압축된 결론만 담는다. 원본은 해당 시점 Report에 남아 있으므로 Memory에서 링크만 참조한다.

Memory와 Lessons Learned 파일 자체는 현재 일반 하네스 필수 문서가 아니다(§4 정의). 실제 프로젝트에 하네스를 부착하는 시점에 그 프로젝트 폴더 안에 생성하며, 지금 일반 하네스에는 이 승격 경로와 최소 형식만 둔다.

## 5. 작업 기본 흐름

일반 작업 흐름은 `09.AGENT_WORKFLOW.md §2`가 소유한다.

이 문서에서는 전체 흐름을 아래 수준으로만 요약한다.

```txt
요청 → Quick Ref/Context 확인 → Skill/Gate 선택 → GateGuard 위험 판정 → 작업 → Gate 검증 → Report/Working Context 반영
```

상세 순서, 작업 계약, 실패/중단 후 재개 절차는 `09.AGENT_WORKFLOW.md`를 따른다.

## 6. 위험 작업 처리 원칙

이 표는 위험 유형 분류의 요약이다. 각 유형의 정확한 해제 조건(사용자 확인이 근거로 대체 가능한지, AND인지 OR인지)은 `04.GATEGUARD.md §6-1`이 유일하게 소유하며, 이 표는 그 조건을 다시 정의하지 않는다(외부 검수 M-13).

| 위험도 | 예시 | WARN 처리 | FAIL 처리 |
|---|---|---|---|
| 일반 작업 | 단일 문서 문구 수정, 단순 설명 보강 | 기록 후 제한 진행 가능 | 수정 후 재검증 |
| 구조 작업 | 폴더 구조 변경, 문서 번호 변경, 스킬 추가/삭제 | `04.GATEGUARD.md §6-1` 기준 확인 전 수정 금지 | 진행 금지 |
| 데이터 작업 | DB 스키마, 마이그레이션, 대량 데이터 수정 | `04.GATEGUARD.md §6-1` 기준 확인 전 수정 금지 | 진행 금지 |
| 보안 작업 | 인증, 권한 | `04.GATEGUARD.md §6-1` 기준 확인 전 수정 금지(승인과 Security Gate PASS 둘 다 필요) | 진행 금지 |
| 결제 작업 | 결제, 환불, 웹훅 | `04.GATEGUARD.md §6-1` 기준 확인 전 수정 금지(예외 없음) | 진행 금지 |
| 파일 손상 가능 작업 | 삭제, 대량 이동, 덮어쓰기 | 사용자 확인 전 진행 금지(예외 없음) | 진행 금지 |
| 외부 실행 | 외부 설치 스크립트, 공급망 영향 | 사용자 확인 전 진행 금지(예외 없음) | 진행 금지 |
| 환경 변경(비파괴적) | 로컬 환경변수, 설정 파일 값 수정 | `04.GATEGUARD.md §6-1` 기준 확인 전 수정 금지 | 진행 금지 |
| 위험 터미널 명령 | 대량 삭제, 시스템 설정 변경 명령 | 사용자 확인 전 진행 금지(예외 없음) | 진행 금지 |

## 7. 금지 사항

| 금지 항목 | 이유 |
|---|---|
| 근거 없이 파일 구조를 바꾸기 | 기존 규칙과 연결 구조가 깨질 수 있음 |
| 사용자 변경을 확인하지 않고 덮어쓰기 | 기존 작업 손실 가능 |
| 삭제/대량 이동을 확인 없이 진행 | 복구 비용이 큼 |
| 스킬을 중복 생성하기 | Skill Index가 불필요하게 복잡해짐 |
| 결제/보안/인증 기능을 일반 기능처럼 가볍게 처리하기 | 금전·권한·개인정보 리스크가 큼 |
| 외부 설치 스크립트 실행을 기본값으로 두기 | 공급망·보안 위험이 있음 |
| 대규모 Hook 자동 차단을 초기부터 강제하기 | 오작동 시 작업 흐름이 멈출 수 있음 |
| 문서만 만들고 검수 기준을 두지 않기 | 형식은 있어도 실제 품질을 보장하기 어려움 |

## 9. 변경 원칙

하네스 문서를 수정할 때는 다음을 지킨다.

1. 수정 이유를 명확히 남긴다.
2. 관련 문서와 스킬 인덱스를 함께 확인한다.
3. 새 규칙이 기존 규칙과 충돌하지 않는지 확인한다.
4. 위험 작업은 `04.GATEGUARD.md`를 먼저 통과한다.
5. 자동 검증 가능한 항목은 scripts 또는 gates에 반영한다.
6. 자동화가 어려운 항목은 checklists에 남긴다.
7. 수정 후 Report와 Working Context의 책임을 구분해서 기록한다.

## 10. 자동 검증 PASS의 한계

`scripts/*.mjs`의 PASS는 **구조 검증 통과**만을 뜻한다.

세부 한계와 스크립트별 보증 범위는 `08.QUALITY_GATE.md §10`을 따른다.

## 선택적 export 검증

- 기본 배포와 공식 반영에는 ZIP 생성이나 `validate-package.mjs` 실행이 필요하지 않다.
- 사용자가 ZIP export를 명시적으로 요청한 경우에만 `scripts/validate-package.mjs`로 해당 ZIP의 이름·내부 구조를 검증한다.
- export 파일은 Git 이력을 대체하지 않으며, 공식 반영 여부도 바꾸지 않는다.
