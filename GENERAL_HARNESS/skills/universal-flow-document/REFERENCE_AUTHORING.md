# Reference: 흐름 분석·표현·검수

> `skills/universal-flow-document/SKILL.md`의 보조 문서다. 흐름 작성·갱신 때 읽는다.

## 의미와 근거

Entry Point별 흐름을 나눈다. HTTP, CLI, 스케줄러, 이벤트 소비, 콜백, 스트림, UI, 사람이 수행하는 업무를 모두 허용한다. 소스에서 실행 경로를 추적하고 단순 getter·변환·wrapper는 업무 의미가 없으면 노드로 만들지 않는다.

| 타입 | 표현할 의미 |
|---|---|
| start / success / failure | 시작 / 성공 종료 / 실패 종료; 둥근 도형 |
| process | 핵심 처리; 사각형 |
| decision | 조건 판단; 마름모, 구별되는 분기 라벨 |
| input_output | 입력·출력; 평행사변형 |
| database | 실제 영속 저장소 조회/변경; 원통형 |
| external | 외부 시스템 호출; 이중 테두리 |
| event / async / callback / stream | 발행·비동기·재진입·연속 처리; 타입 배지와 선 의미 |
| note | 부연 설명; 실행 경로에서 제외 |

위→아래가 기본이다. 좌우 분기는 column, 단계는 row로 배치한다. 선은 sync/success/failure/async/callback/compensation 의미를 구분한다. 색만으로 의미를 전달하지 않는다. async·callback·compensation은 점선과 라벨을 함께 쓴다. 재시도는 실제 조건·종료 경로와 함께 설명한다. Stream의 종료는 연결 종료나 이번 설명 범위의 종료를 뜻하며 영구 서비스 자체의 종료로 오해시키지 않는다.

## 설명과 갱신

짧은 title과 상세 description을 분리한다. why, inputs, outputs, failures, source는 확인된 만큼 채우고 미확인은 확인 필요라고 쓴다. 소스에는 파일/문서, 심볼/줄, revision을 남긴다. 기존 ID를 유지해 변경 근거를 추적하며 예시 도메인을 실제 업무에 복제하지 않는다.

## 수동 검수

- 주요 노드·분기가 코드/업무 규칙에 존재하는지 대조한다. 구조 검사는 실제 근거의 진위를 인증하지 않는다.
- 기본 전체 보기와 결과별 버튼·하위 시나리오 선택은 `skills/universal-flow-document/REFERENCE_INTERACTION.md`를 따른다. 시나리오는 path의 인접 순서로 선을 강조한다.
- 노드 클릭/Enter/Space와 설명 버튼이 같은 ID를 선택하는지 확인한다.
- 좁은 화면에서 목록 토글·검색·차트 가로 이동·설명 줄바꿈을 확인한다. 차트는 SVG 전체 높이만큼 펼치고 내부 세로 스크롤을 만들지 않는다. 긴 흐름은 페이지의 자연스러운 세로 스크롤로 읽으며 페이지 전체 가로 넘침은 수정한다.
- 도형·선·라벨 겹침은 브라우저에서 확인하고 row/column을 조정한다. 자동 배치 최적화나 선 교차 제거를 보장하지 않는다.
- 포커스 표시, 조작 요소 이름, 대비, reduced motion을 확인한다.

판정은 상위 스킬의 Quality Gate와 기존 Document Gate를 따른다.

## 상세도와 범위 대조

상세 요청은 detailed로 작성한다. 개요 요청은 overview로 두되 왜 생략했는지 coverage에 남긴다. 전체 개요와 상세 흐름은 같은 문서에 두고 flowRef로 연결한다. Flow 수를 늘리기 위해 같은 경로를 복제하지 않는다. 표본 검수는 표본임을 밝히고 전체 검수라고 보고하지 않는다.

분석 시 Entry Point·업무 결과 목록 → 관련 호출/규칙 → Flow ID를 대조한다. 각 coverage에는 포함 범위·대조 기준·제외/미확인을 남긴다. 원본 문서의 PASS·스크린샷 목록은 과거 주장으로 읽고 이번 검수 결과로 재사용하지 않는다.

## 단계 분리와 설명 기준

- 독립적인 업무 판단, 중요한 상태 변경, 잠금·커밋·롤백, 외부 호출, 사용자 결과를 바꾸는 실패, 비동기 위임을 별도 노드 후보로 삼는다.
- getter·DTO 변환·로그·wrapper는 기본 생략하되 권한·정합성·결과를 바꾸면 남긴다.
- owner는 사용자/Agent/서비스/저장소 등 실제 주체다. condition은 무엇을 어떤 값·상태와 비교하는지 적는다. ‘조건 확인’ 같은 제목을 복사하지 않는다.
- outputs에는 다음 단계가 받는 결과를, stateChange에는 중요한 변경 전/후를 적는다. 모든 단계에 억지 상태 변화를 만들지 않는다.
- 제목은 짧게, description은 1~3문장, 근거·계약은 펼쳐보기로 분리한다. why는 자명하지 않을 때만 쓴다. 전문 용어는 첫 설명에서 풀이한다.
- 실제 구현, 명세/설계, 설정 활성화가 필요한 기능, 미확인을 status로 구분한다. 화면 연결 설계가 실제 구현 완료를 뜻하지 않도록 한다.

## 실패·보류·후속 처리

- failureCases에 발생 nodeId, 연결 scenarioId, 구체적 condition, effect, nextAction을 묶는다. API이면 status/code도 적고 재시도 조건·한도 또는 금지를 명시한다. 근거가 불명확하면 확정 코드를 만들지 않는다.
- 인증·권한·입력·상태 충돌·리소스 없음·외부 장애·보상 실패 중 결과가 다른 경우를 구분한다. 같은 의미의 공통 실패는 진입 공통 단계에서 묶는다.
- 실패선은 실제 발생 노드에서 출발한다. 미진행 단계와 실패 후 실행되는 정리/보상 단계를 혼동하지 않는다. fallback 후 정상 결과는 success로 끝날 수 있다.
- hold는 승인/추가 근거를 기다리는 보류다. failure와 구분하며 재개 조건을 설명한다. 스킬의 Gate WARN과 실행 흐름의 종료 타입은 서로 다른 개념이다.
- 202 같은 접수 완료, 후속 작업 완료, 결과 콜백/조회 전달은 completion으로 구분한다. 비동기선은 완료 응답 뒤가 아니라 위임/등록 단계에서 분기한다. 콜백은 필요하면 별도 entry 또는 연결된 상세 Flow로 둔다.
- 트랜잭션 커밋 전/후 이벤트, 롤백 범위, 외부 파일 보상 삭제, 잠금·세션 폐기처럼 결과를 바꾸는 사실을 누락하지 않는다. 코드/규칙이 뒷받침하는 범위만 설명한다.

## 검수 범위

내용 검수는 원본의 Entry/분기/상태 변화와 대조한다. 자동 검수는 필수 상세 필드·경로·실패 연결·안전한 URL만 보증한다. HTML의 동작·화면·접근성 검수는 `skills/universal-flow-document/REFERENCE_UI_REVIEW.md`, 색상·배치는 `skills/universal-flow-document/REFERENCE_VISUAL.md`가 소유한다. 번호·주체·근거와 실제 시나리오 경로도 함께 대조한다.
