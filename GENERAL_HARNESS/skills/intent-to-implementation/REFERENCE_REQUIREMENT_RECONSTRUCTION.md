# Reference: 요구사항 재구성

> `skills/intent-to-implementation/SKILL.md`의 보조 참조 문서다. 단독 스킬이 아니며, 상위 스킬의 Harness Control Rule을 그대로 따른다.

사용자의 말과 프로젝트 증거로부터 **가장 작은 신뢰 가능한 명세**를 복원한다.

## 증거 우선순위

1. 사용자의 명시적 현재 지시
2. 제공된 요구사항·완료 조건 문서
3. 저장소 내 지침 문서
4. 기존 동작, 테스트, 스키마, 인터페이스
5. 확립된 프로젝트 관례
6. 저위험 업계 기본값

하위 순위의 관례로 상위 순위의 근거를 덮어쓰지 않는다. (이 순서는 요구사항 판단용이며, 규칙 충돌 시 우선순위는 `00.HARNESS_RULES.md §3`이 소유한다.)

## 요구사항 맵

내부 판단용 압축 맵을 만든다. 과제와 관련 있는 항목만 사용한다.

| 항목 | 질문 |
|---|---|
| 행위자 | 누가 이 동작을 시작하는가? |
| 트리거 | 어떤 요청/이벤트/행동이 시작점인가? |
| 입력 | 어떤 데이터가 필요하고 어디서 오는가? |
| 규칙 | 어떤 검증·권한·비즈니스 규칙이 적용되는가? |
| 상태 변화 | 무엇이 생성/수정/삭제되는가? |
| 출력 | 어떤 응답·UI 상태·이벤트·부수효과가 기대되는가? |
| 실패 | 입력·상태가 잘못됐을 때 무엇이 일어나야 하는가? |
| 완료 | 어떤 관찰 가능한 증거가 동작을 증명하는가? |

## 신뢰도 라벨

- **Confirmed**: 사용자가 직접 말했거나 원본 자료에서 직접 확인한 사실
- **Inferred**: 기존 코드·프로젝트 관례·저위험 기본값이 뒷받침하는, 되돌릴 수 있는 선택
- **Unresolved**: 신뢰할 근거가 없는 중대한 결정

Inferred를 사용자 요구사항인 것처럼 제시하지 않는다. 리뷰에 영향을 주는 Inferred는 최종 응답에서 언급한다. Unresolved 중 중대한 결정(공개 계약·DB·보안·결제·비가역 작업)은 추측하지 않고 질문한다.

## 명세 문서 기반 작업

요구사항 문서가 있으면:

1. 원자적 요구사항 단위로 추출한다.
2. 각 요구사항을 코드/설정/데이터/UI/테스트에 매핑한다.
3. 이미 구현됨 / 부분 구현 / 미구현 / 모순 항목을 표시한다.
4. 의존 관계를 식별하고 구현 순서를 정한다.
5. 구현하는 요구사항마다 확인 방법을 정의한다.

문서의 모든 문장이 현재 범위에 속한다고 가정하지 않는다. MVP·제외 범위·후순위 표기가 있으면 존중한다.

## 완료 기준 작성

관찰 가능한 결과로 적는다.

좋은 예:

- 인증된 사용자는 게시물당 좋아요를 1개만 만들 수 있다
- 반복 요청이 중복 행을 만들지 않는다
- 좋아요 취소 시 표시 개수가 줄어든다
- 미인증 요청은 프로젝트 표준 에러 응답을 받는다

나쁜 예: "정상 동작한다", "코드가 깔끔하다"
