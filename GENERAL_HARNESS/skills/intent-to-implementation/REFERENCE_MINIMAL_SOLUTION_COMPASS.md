# Reference: 최소 해법 나침반

> `skills/intent-to-implementation/SKILL.md`의 보조 참조 문서다. 단독 스킬이 아니며, 상위 스킬의 Harness Control Rule을 그대로 따른다.
>
> 소유권: 이 문서는 `CLAUDE.md §2`(Simplicity First)·`§3`(Surgical Changes) 원칙의 **실행 절차**다. 그 원칙을 재정의하거나 약화하거나 대체하지 않으며, Gate·Checklist가 요구하는 항목을 이 문서를 근거로 생략할 수 없다.

짧은 이정표로 작업 방향을 잡되, 사용자에게 보이는 응답에서 구호처럼 반복하지 않는다.

## 쌓기 전에 내려가기

아래 순서로 묻고, 처음으로 충분한 답이 나오는 지점에서 멈춘다.

1. **만들기 전에 필요 확인** — 요청과 현재 동작을 볼 때 코드 변경이 실제로 필요한가?
2. **만들기 전에 찾기** — 저장소에 이미 그 동작·헬퍼·패턴·확장 지점이 있는가?
3. **추가하기 전에 활용** — 설정, 표준 라이브러리, 런타임, 브라우저, DB, 프레임워크로 해결되는가?
4. **새로 만들기 전에 재사용** — 이미 설치된 의존성이나 확립된 컴포넌트로 일관되게 해결되는가?
5. **추상화 전에 직접** — 책임 있는 컴포넌트에 작은 지역 변경으로 규칙을 명확히 표현할 수 있는가?
6. **구조화 전에 증명** — 어떤 구체적 반복·변형·소유권 경계·수명 주기가 새 추상화를 요구하는가?

이 체크리스트는 사용자가 근거나 설계 대안을 물을 때만 보여준다. 결과에 자연스럽게 반영되게 한다.

**침묵은 사용자 응답에만 적용되고 기록에는 적용되지 않는다.** 결과를 바꾼 판단(의존성을 추가하지 않은 이유, 추상화를 만들지 않은 이유, 기존 코드를 재사용한 이유)은 `06.REPORT_TEMPLATE.md` 기준 Report에 기록한다.

## 탐색 근거

결정에 영향을 준 검색 경로·후보·제약과 재사용/확장/신규 선택 이유를 기존 Report에 짧게 남긴다. 저장소 → 내장 기능 → 이미 설치된 의존성 순서를 유지하며, 외부 탐색은 내부에서 충분한 답을 얻지 못했을 때만 수행한다. 접근할 수 없는 검색 채널은 '조회 불가'이지 '결과 없음'이 아니다. 검색했다는 이유로 패키지·MCP 설치가 승인되지는 않는다.

이 절은 ECC search-first의 탐색 근거 원칙을 재작성한 부분이다. 기존 최소 해법 전체의 출처를 ECC로 변경하지 않는다. 원 고지는 `skills/intent-to-implementation/LICENSE`, 출처 범위는 `_SOURCE_MAPPING.md`에 있다.

## 작다는 것은 충분하다는 뜻이다

- 고유한 책임이 없는 단계·파일·계층·개념을 제거한다.
- 분리가 재사용·소유권 가치 없이 탐색 비용만 늘리면 코드를 유일한 호출자 근처에 둔다.
- 공유 동작 추출은 실제 반복, 의미 있는 변형, 독립적 수명 주기가 확인될 때 한다 — 추출이 가능하다는 이유만으로 하지 않는다.
- 두 번째 아키텍처 스타일을 도입하기보다 프로젝트의 기존 형태를 따른다.
- 동작을 감추는 압축된 코드보다 읽히는 분기와 이름 있는 연산을 택한다. 단순함의 척도는 줄 수가 아니라 총 유지보수 비용과 동작의 명확성이다.
- 작고 안정적이며 기존 역량으로 안전하게 처리되는 동작을 위해 의존성을 추가하지 않는다.
- 마이그레이션 비용, 테스트 부담, 운영 동작, 미래 제거 비용도 복잡도로 계산한다.

## 지우기 전에 추적하기

코드를 삭제·통합·우회하기 전에:

1. 보이는 증상이 아니라 근본 원인을 식별한다
2. 관련된 모든 호출자·구현·설정·테스트·런타임 경로를 검색한다
3. 죽은 코드와 숨은 계약을 지키는 코드를 구분한다
4. 파괴적 변경이 승인되지 않았다면 호환성을 보존한다
5. 단순화한 경로를 동작 중심 검사로 검증한다

지역 정리 요청을 저장소 전체 삭제·재설계로 확장하지 않는다.

**위 단계를 완료해도 그것이 승인은 아니다.** 삭제, 대량 이동, 덮어쓰기는 `04.GATEGUARD.md §6-1`에 따라 진행 전 사용자 승인이 항상 필요하다(예외 없음).

## 안전은 장식이 아니다

다음이 필요한 상황에서는 약화·제거로 단순화하지 않는다:

- 인증·권한 경계
- 입력 검증·출력 인코딩
- 데이터 무결성, 트랜잭션, 멱등성, 동시성 보장
- 리소스 정리, 타임아웃, 재시도 한도, 실패 처리
- 개인정보, 감사, 로깅, 관측 요구사항
- 접근성 동작
- 호환성·공개 계약
- 의미 있는 동작을 보호하는 테스트

이 중 하나가 불필요해 보이면, 호출 지점·계약·테스트에서 증거를 확보한 뒤에만 변경한다.

## 결정 테스트

관련된 모든 질문에 "예"라고 답하는 가장 작은 선택지를 고른다:

- 확정된 완료 기준을 전부 충족하는가?
- 책임의 위치가 명확한가?
- 유지보수자가 숨은 마법을 재구성하지 않고 실행 경로를 이해할 수 있는가?
- 프로젝트의 계약과 안전 경계를 보존하는가?
- 초점 있는 증거로 검증할 수 있는가?

두 선택지가 모두 통과하면 새 개념이 더 적은 쪽을 택한다. 어느 쪽도 통과하지 못하면 추측하지 말고 빠져 있는 중대한 결정을 질문한다.
