# Reference: 의도 라우팅

> `skills/intent-to-implementation/SKILL.md`의 보조 참조 문서다. 단독 스킬이 아니며, 상위 스킬의 Harness Control Rule을 그대로 따른다.

현재 요청에서 가장 강한 **명시적 동사**를 기준으로 판단한다. 호기심 표현을 파일 수정 권한으로 해석하지 않는다.

| 사용자 표현 | 기본 모드 | 허용 행동 |
|---|---|---|
| "이게 뭐야?", "설명해줘" | 설명 | 읽고 설명 |
| "어떻게 만들까?", "어떤 식으로 해야 해?" | 계획 | 조사하고 제안 |
| "구조를 잡아줘", "설계해줘" | 설계 | 구조/계획 산출. 수정은 명시 요청 시에만 |
| "원인을 찾아줘", "왜 이래?" | 진단 | 조사하고 원인 식별 |
| "구현해줘", "추가해줘", "만들어줘" | 구현 | 요청 범위 안에서 수정하고 검증 |
| "고쳐줘", "해결해줘" | 수정 | 진단 → 수정 → 검증 |
| "리팩터링해줘" | 리팩터링 | 동작 변경 언급이 없으면 동작 보존 |
| "확인해줘", "테스트해줘" | 검증 | 안전한 검사 실행. 몰래 고치지 않음 |
| "힌트만 줘" | 학습 보조 | 단계적 힌트 제공. 전체 해답은 보류 |

## 혼합 요청

- "어떻게 할까?" 후에 "그대로 구현해줘"가 오면 계획에서 구현으로 전환한다.
- 구현과 설명을 함께 요청하면 먼저 구현·검증하고, 검증된 결과를 설명한다.
- 최신 지시가 범위를 좁히면 좁은 범위를 따른다.
- 진단 중 권한 범위 밖의 수정거리를 발견하면 보고하고 방향을 묻는다.

## 자율 판단 수위

### 질문 없이 진행 가능(저위험 추론)

되돌릴 수 있고 저장소가 강하게 암시하는 선택:

- 기존 관례를 따르는 이름 짓기
- 현재 구조를 따르는 파일 배치
- 이미 채택된 라이브러리·패턴 사용
- 기존 테스트 옆에 초점 있는 테스트 추가

### 결정 전 질문 필수

답이 달라지면 결과가 실질적으로 바뀌는 것:

- 공개 API 계약
- DB 스키마 또는 파괴적 마이그레이션
- 인증·권한 정책
- 결제·과금·개인정보·보안 동작
- 서비스 간 소유권 경계
- 의미 있는 신규 의존성·인프라
- 배포·공개

가능하면 한 번에 하나씩, 짧은 질문으로 묻는다. 이 목록의 위험 유형별 정확한 해제 조건은 `04.GATEGUARD.md §6-1`이 소유한다.
