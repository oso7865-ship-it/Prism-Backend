# Verification Loop

> 목적: 코드 구현 작업이 끝났을 때, "완료"라고 보고하기 전에 반드시 통과해야 하는 검증 순서를 정리한다.
> 사용 위치: `GENERAL_HARNESS` 공통 스킬
> 출력물: 구현 완료 판정과 검증 근거

---

## 0. Harness Control Rule

- 이 스킬은 `00.HARNESS_RULES.md`의 하위 모듈이다.
- 충돌 시 이 스킬의 절차를 중단하고 `00.QUICK_REF.md`와 `00.HARNESS_RULES.md §3` 우선순위에 따라 상위 규칙을 따른다. 위험 작업 WARN은 사용자 확인 전 스킬 단독으로 진행하지 않는다.

---

## 1. Trigger

- 기능 구현 또는 리팩터링을 마치고 완료로 보고하기 전
- API/DB 명세와 실제 구현이 일치하는지 확인해야 할 때
- 여러 파일을 수정한 뒤 회귀 여부를 확인해야 할 때
- `release-checklist`를 적용하기 전 구현 단계에서 미리 점검할 때

---

## 2. Do Not Trigger

- 설계/문서 초안만 작성하고 실행 가능한 코드가 없는 경우
- 사용자가 명시적으로 "검증 없이 초안만" 요청한 경우

검증 명령이 프로젝트에 아직 정의되지 않아 실행 대상이 없는 경우는 Do Not Trigger가 **아니다** — 이 스킬은 그대로 발동하되, 검증을 건너뛰지 않고 "검증 명령 없음"을 미해결 항목으로 기록한다.

---

## 3. Required Inputs

| 입력물 | 필요 이유 |
|---|---|
| 실제 수정한 파일 목록 | 검증 범위를 확정 |
| 프로젝트에서 사용하는 빌드/타입체크/린트/테스트 명령 | 실행 대상 확인. 명령은 프로젝트마다 다르며 이 스킬은 명령 자체를 고정하지 않는다 |
| 관련 API/DB 명세 | 구현과 명세 일치 여부 확인 |
| 변경 전 대비 diff 또는 변경 요약 | 의도치 않은 변경 확인 |
| test-design 시나리오(있는 경우) | 계획한 요구사항과 실제 실행 결과를 연결 |

---

## 4. Procedure

1. 빌드(또는 컴파일)가 성공하는지 확인한다. 실패하면 다음 단계로 넘어가지 않고 원인을 기록한다.
2. 정적 타입 검사 또는 문법 검사가 있다면 실행하고 결과를 요약한다.
3. 린트/코드 스타일 검사가 있다면 실행하고 결과를 요약한다.
4. 테스트가 있다면 실행하고 통과/실패 개수를 기록한다. 테스트가 없다면 "테스트 없음"을 미해결 항목에 남긴다.
5. 테스트 중 건너뛴(SKIP) 항목이 있으면, 건너뛴 이유가 "이 플랫폼/환경에서는 원래 실행 대상이 아님"인지 "전제 조건을 준비하지 못해서 건너뜀"인지 구분한다. 후자는 SKIP이 아니라 FAIL로 간주한다 — 전제 조건을 갖추지 못한 것은 통과가 아니라 실패다.
6. 변경 전후 diff 또는 변경 요약을 검토해 요청 범위 밖의 수정이 없는지 확인한다. 코드·테스트 품질 검토가 요청되었거나 구체적 구조 우려가 있으면 `skills/code-review/SKILL.md`를 적용한다. 리뷰 산출물의 품질 판정과 검토 대상 코드의 미해결 결함은 분리한다. 확인된 결함은 실제 영향과 관련 Gate에 따라 처리하고 리뷰 PASS만으로 해제하지 않는다.
7. API/DB 명세와 실제 구현이 일치하는지 확인한다.
   UI 기능·데이터·세션 변경이면 `checklists/ui-ux-checklist.md §1-3`, 별도 AI Runtime 연동이면 `checklists/ai-runtime-integration-checklist.md`를 적용한다. mock 결과를 실제 연동 결과로 보고하지 않는다. 변경과 무관한 항목은 사유를 기록하고 범위에서 제외한다.
8. 위 단계 중 하나라도 FAIL이면: 원인이 이미 명확한 단순 실패(오타, 누락된 import 등)면 직접 수정하고 같은 단계부터 재검증한다. 원인이 불명확하거나 같은 FAIL이 반복되면 `skills/agent-recovery/SKILL.md`로 연결해 진단한다(`skills/agent-recovery/SKILL.md §2`의 Do Not Trigger와 일치).
9. 시나리오가 있으면 각 ID별 실제 명령·결과·미실행 이유를 연결한다. 설계 PASS, 코드 작성, 실행 PASS를 구분하며 버그 수정은 동일 대상의 재현 실패/수정 후 통과 증거를 남긴다(없으면 없다고 기록). 결과를 `06.REPORT_TEMPLATE.md`에 남긴다.

이 스킬은 빌드/테스트 명령 이름을 고정하지 않는다. 프로젝트마다 실제 명령은 다르며, 어떤 명령을 썼는지는 Report에 기록한다.

---

## 5. Quality Gate

| 판정 | 기준 |
|---|---|
| PASS | 빌드, 정적 검사, 테스트(있는 경우)가 모두 통과했고 명세와 구현이 일치하며 범위 밖 변경이 없음. 건너뛴 테스트가 있다면 전부 환경상 정당한 SKIP임 |
| WARN | 빌드/검사는 통과했으나 테스트가 없거나 일부 항목을 확인하지 못함. 위험 작업(DB/결제/보안 관련 구현)이면 위험 WARN으로 분류해 `04.GATEGUARD.md` 기준을 따름 |
| FAIL | 빌드 실패, 테스트 실패, 명세와 구현 불일치, 요청 범위 밖 변경이 확인됨, 또는 전제 조건 미비로 건너뛴 테스트를 SKIP으로만 처리하고 넘어감 |

---

## 6. Output Format

```md
## Verification Loop 결과

- 사용 이유:
- 확인한 입력물:
- 실행한 검증(빌드/타입체크/린트/테스트): 명령과 결과
- 명세-구현 일치 여부:
- 범위 밖 변경 여부:
- PASS/WARN/FAIL:
- 위험 WARN 여부:
- 다음 연결:
```

---

## 7. Handoff

다음 연결: `skills/agent-recovery/SKILL.md`(검증 실패 시) → `skills/quality-gate/SKILL.md`(이 산출물에 해당하는 모든 Gate를 `08.QUALITY_GATE.md`의 §7-2 매트릭스로 선택·집계 — 이 스킬은 어떤 Gate가 필요한지 직접 나열하지 않는다) → `checklists/release-checklist.md`(제출·배포 전일 때만 적용 — `checklists/release-checklist.md`의 §0 "적용 범위" 행 참고) → `06.REPORT_TEMPLATE.md`

---

## 8. Anti-Patterns

- 빌드/테스트를 실행하지 않고 "완료"로 보고하기
- 실패한 검증을 다음 단계로 그냥 넘기기
- 검증 명령을 프로젝트 것으로 확인하지 않고 임의로 추측해서 실행하기
- 명세와 구현이 다른데 구현을 기준으로 명세를 조용히 바꿔버리기
- 전제 조건을 못 갖췄다는 이유로 테스트를 SKIP 처리하고 실패로 보고하지 않기
