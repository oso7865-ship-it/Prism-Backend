# Test Design

> 목적: 확정된 요구사항·위험을 필요한 검증 시나리오와 기대 결과로 바꾼다.
> 출력물: 요구사항과 테스트 위치·수준·데이터를 연결한 설계표.
> 출처: ECC tdd-workflow의 행동 검증·실패 후 통과 증거 원칙을 재작성했다. 원 고지는 `skills/test-design/LICENSE`, 범위는 `_SOURCE_MAPPING.md`에 있다.

## 0. Harness Control Rule

- 이 스킬은 `00.HARNESS_RULES.md`의 하위 모듈이다.
- 충돌 시 중단하고 상위 규칙을 따른다. 위험 작업 WARN은 사용자 확인 전 스킬 단독으로 진행하지 않는다.

## 1. Trigger

- 새 업무 규칙, 권한·상태 전이 변경, 재발 버그를 검증할 시나리오가 부족할 때.
- 중요한 변경의 완료 기준과 기존 테스트가 연결되지 않을 때.

## 2. Do Not Trigger

- 문구·단순 시각 수정, 실행 대상 없는 설명.
- 변경에 대응하는 테스트 설계가 이미 유효한 경우.
- 기존 테스트 품질만 검토하는 요청은 `skills/code-review/SKILL.md`로 연결한다.

## 3. Required Inputs

- 확정된 요구사항·완료 기준, 변경 영향 범위, 기존 테스트와 실제 실행 명령.
- 관련된 경우에만 예외·권한·외부 실패 계약. 미정인 정책은 미확정으로 표시한다.

## 4. Procedure

1. 기존 테스트를 찾아 재사용·확장 가능성을 확인한다.
2. 요구사항마다 관측 가능한 기대 결과를 정한다. 미정인 정책을 테스트 편의로 확정하지 않는다.
3. 정상·실패·경계 중 관련된 사례를 고른다. 중복 요청·동시성·멱등성·권한은 해당 계약이 있을 때만 포함한다.
4. 단위·통합·사용자 흐름 중 결함을 관측할 최소 수준과 데이터를 고른다. 실제 외부 연동과 mock으로 검증 가능한 범위를 구분한다.
5. 버그 재현이 가능하거나 테스트 우선 방식을 선택했다면, 같은 대상의 의도한 실패와 수정 후 통과를 연결한다. 환경 누락·문법 오류는 버그 재현 성공이 아니다.
6. 시나리오 ID를 구현·검증 단계에 인계한다. 도구, 커버리지 수치, 단계별 Git 커밋을 전역으로 강제하지 않는다.

## 5. Quality Gate

| 판정 | 기준 |
|---|---|
| PASS | 핵심 요구사항에 기대 결과·수준·데이터·위치가 연결되고 관련 실패 조건을 다룸 |
| WARN | 핵심 계약은 명확하지만 일부 데이터·환경·테스트 위치가 미확정 |
| FAIL | 핵심 요구사항이 빠졌거나 미정 정책을 추측해 테스트 정답으로 고정함 |

설계 PASS와 테스트 실행 PASS는 별개다. 실제 실행 및 SKIP/FAIL 판단은 `skills/verification-loop/SKILL.md`가 소유한다.

## 6. Output Format

| ID | 요구사항·위험 | 시나리오 | 기대 결과 | 수준·데이터 | 테스트 위치·명령 |
|---|---|---|---|---|---|
| 사례 ID | 근거 | 입력·행동 | 관측할 결과 | 필요한 수준 | 재사용/신규/미정 |

- 설계 판정:
- 실행 여부·미실행 이유:
- 재현 실패 증거·수정 후 통과 증거(관측한 경우만):

## 7. Handoff

계약 미정은 `skills/planning/SKILL.md`로 반환한다. 확정된 설계는 구현 후 `skills/verification-loop/SKILL.md`로 넘기며, 기록은 `06.REPORT_TEMPLATE.md`를 따른다.

## 8. Anti-Patterns

- 구현 내부 문자열이나 같은 알고리즘을 복사한 기대값만 검증하기.
- 수치 목표를 채우기 위해 무의미한 테스트를 늘리기.
- 설계 문서만 작성하고 테스트 실행까지 완료했다고 보고하기.
