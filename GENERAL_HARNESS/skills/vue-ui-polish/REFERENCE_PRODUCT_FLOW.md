# Product Flow

> `skills/vue-ui-polish/SKILL.md`의 보조 참조 문서다. 단독 스킬이 아니며, 상위 스킬의 Harness Control Rule(Vue 3 스택 한정 포함)을 그대로 따른다.

## 1. 화면 계약

구현 전에 다음을 한 문장씩 정리하라.

- 사용자: 이 화면을 사용하는 사람
- 상황: 화면에 들어온 이유
- 핵심 과업: 반드시 끝내야 하는 한 가지
- 주요 정보: 결정 전에 알아야 하는 내용
- 완료 기준: 사용자가 성공을 인지하는 방법
- 이탈 경로: 취소·뒤로가기·나중에 하기

정보가 부족해도 저장소에서 복원 가능한 내용은 먼저 조사한다. 결과를 크게 바꾸는 정보만 한 번에 1~3개 질문한다.

## 2. 흐름 작성

정상 경로만 그리지 마라.

1. 진입
2. 정보 확인 또는 입력
3. 검증
4. 처리 중
5. 성공 또는 실패
6. 다음 행동

결제, 인증, 삭제, 제출처럼 되돌리기 어려운 행동은 대상·금액·영향을 행동 직전에 다시 보여준다.

## 3. 상태 모델

기능에 실제로 적용되는 상태만 정의하라.

| 상태 | 사용자에게 보여줄 것 | 가능한 행동 |
| --- | --- | --- |
| 초기 | 목적과 시작점 | 시작·탐색 |
| 로딩 | 무엇을 기다리는지 | 취소가 필요하면 취소 |
| 빈 상태 | 비어 있는 이유 | 첫 항목 만들기·필터 해제 |
| 오류 | 발생한 일과 영향 | 재시도·수정·도움말 |
| 성공 | 완료된 결과 | 다음 과업 |
| 권한 없음 | 제한 이유 | 로그인·권한 요청·돌아가기 |
| 오프라인 | 연결 상태 | 재시도·로컬 작업 |

장식용 상태를 만들지 마라. 예를 들어 단순 링크에 loading·success 상태를 억지로 추가하지 않는다.

## 4. 정보 위계

2초 안에 다음 세 층이 구분되어야 한다.

1. 지금 무엇을 보고 있는가
2. 무엇을 결정하거나 해야 하는가
3. 자세한 정보는 어디에 있는가

크기만으로 위계를 만들지 말고 위치, 간격, 대비, 그룹, 문구를 함께 사용한다. 모든 카드와 버튼을 같은 무게로 만들지 않는다.

## 5. 기능 문구

- 버튼은 실행 결과를 동사로 쓴다: `저장`, `결제하기`, `예약 요청`.
- 제목만 읽어도 오류의 영향을 이해할 수 있게 한다.
- 성공 토스트는 결과가 화면에 보이지 않을 때만 사용한다.
- 제공되지 않은 지표·후기·고객사·성과를 만들지 않는다.
- 개발용 `Lorem ipsum`, `John Doe`, `Acme`를 운영 문구처럼 남기지 않는다.
- 사용자의 전문 수준에 맞는 용어를 사용하고 내부 구현 용어를 노출하지 않는다.

## 6. 와이어프레임 체크

- 모바일 단일 열에서 주요 과업이 완결되는가
- 주요 행동이 한 화면에 여러 개 경쟁하지 않는가
- 위험 행동과 일반 행동이 충분히 분리됐는가
- 필수 정보가 장식 아래로 밀리지 않는가
- 로딩·빈 상태·오류에서 레이아웃이 붕괴하지 않는가
- 키보드와 화면 읽기 순서가 시각적 순서와 일치하는가
