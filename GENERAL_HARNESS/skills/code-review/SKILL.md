# Code Review

> 목적: 기존 코드·diff·테스트의 결함과 유지보수 위험을 구체적 근거로 검토한다.
> 출력물: 범위와 한계, 위치·증상·영향·수정안이 연결된 검토 결과.
> 출처: brooks-lint의 review/test 및 공통 검수 원칙을 재작성했다. 원 MIT 고지는 `skills/code-review/LICENSE`, 고정 출처는 `_SOURCE_MAPPING.md`에 있다.

## 0. Harness Control Rule

- 이 스킬은 `00.HARNESS_RULES.md`의 하위 모듈이다.
- 충돌 시 중단하고 상위 규칙을 따른다. 위험 작업 WARN은 사용자 확인 전 스킬 단독으로 진행하지 않는다.

## 1. Trigger

- 코드·PR·diff 또는 기존 테스트의 검토를 요청받았을 때.
- 변경 검증 중 호출자 영향, 숨은 계약, 테스트 신뢰성에 구체적인 우려가 발견됐을 때.

## 2. Do Not Trigger

- 신규 코드 작성법이나 언어 문법 설명, 문서만의 오타 검수.
- 빌드·테스트 실행만 필요한 경우는 `skills/verification-loop/SKILL.md`를 사용한다.
- 저장소 전체 아키텍처 감사·부채 로드맵·자동 일괄 수정을 이 스킬로 확장하지 않는다.

## 3. Required Inputs

- 검토 요청과 범위, 실제 코드 또는 비교 기준과 diff, 관련 호출자·계약·테스트.
- 변경 목적과 제약. 전체를 확인할 수 없으면 확인한 범위를 명시한다.

## 4. Procedure

1. 리뷰와 수정 권한을 구분한다. 검토 요청만 있으면 대상 코드를 변경하지 않는다. 범위가 없으면 관련 변경을 확인해 범위를 명시하며 저장소 전체로 자동 확대하지 않는다.
2. 변경 동작과 호출자를 추적한다. 실제 결함, 변경 전부터 존재한 문제, 개선 제안을 구분한다.
3. 이해하기 어려운 실행 경로, 변경 영향 확산, 업무 규칙 중복, 불필요한 복잡성, 의존성 순환, 업무 의미의 불일치를 살핀다. 함수 길이·파일 수·특정 아키텍처 취향만으로 결함을 확정하지 않는다.
4. 테스트를 검토할 때만 `skills/code-review/REFERENCE_TEST_REVIEW.md`를 읽는다. 기존 테스트의 검수와 새 테스트 설계를 구분한다.
5. 각 지적에 파일·줄/심볼, 관측한 증상, 적용 계약·원칙, 실제 영향과 발생 조건, 최소 수정안, 확인 방법을 연결한다. 근거가 부족한 것은 확인 질문으로 분리한다. 책의 권위나 위험 점수만으로 지적을 만들지 않는다.
6. 영향과 재현 가능성으로 우선순위를 정한다. 같은 원인의 지적은 묶고, 확인한 범위에서 지적이 없으면 없다고 적는다. 실행하지 않은 테스트는 명시한다.
7. 수정까지 요청받았다면 확인된 문제만 최소 수정하고 원래 실패 조건·관련 회귀를 재검증한다. 실패 반복은 `skills/agent-recovery/SKILL.md`로 연결한다. 무제한 sweep이나 자동 커밋은 하지 않는다.

## 5. Quality Gate

| 판정 | 기준 |
|---|---|
| PASS | 검토 범위·한계가 명확하며 모든 지적이 실제 위치·영향·수정안·검증 방법과 연결되거나 근거 있는 지적 없음으로 기록됨 |
| WARN | 호출자·환경을 확인하지 못해 일부 결론이 제한됨 |
| FAIL | 추정·스타일 선호를 결함으로 단정하거나 읽기 전용 요청에서 코드를 수정함 |

이 표는 **리뷰 산출물의 품질** 판정이다. 대상 코드의 결함이 해결됐다는 판정이 아니다. 결함별 심각도(Critical/Major/Minor), 해결 상태, 검증 결과를 별도로 남기고 적용 Gate 및 verification-loop에 인계한다. 점수로 기존 FAIL을 낮추지 않는다.

## 6. Output Format

- 검토 범위·비교 기준·미확인 범위:
- 지적별 위치 / 증상 / 계약·원칙 / 발생 조건과 영향 / 최소 수정안 / 확인 방법:
- 결함별 심각도·해결 상태:
- 실행한 검사·미실행 검사:
- 리뷰 산출물 판정 / 대상 코드의 남은 결함:

## 7. Handoff

수정 계획이 필요하면 `skills/planning/SKILL.md`, 검증 설계가 부족하면 `skills/test-design/SKILL.md`, 실제 수정 후에는 `skills/verification-loop/SKILL.md`로 연결한다. 대상에 해당하는 Gate 선택은 `skills/quality-gate/SKILL.md`, 기록은 `06.REPORT_TEMPLATE.md`를 따른다.

## 8. Anti-Patterns

- 긴 함수나 특정 계층 구조만으로 Critical을 부여하기.
- 테스트 통과를 이유로 약한 assertion이나 숨은 계약을 무시하기.
- 리뷰 품질 PASS를 코드 무결함·병합 가능 판정으로 사용하기.
- 검토 지적을 근거로 요청하지 않은 전체 리팩터링을 시작하기.
