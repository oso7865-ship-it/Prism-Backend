# UI/UX Design

> 목적: 화면 설계 요구사항을 사용자 목표·흐름·상태·반응형·접근성·구현 가능성까지 갖춘 실행 가능한 산출물로 만든다.
> 사용 위치: `GENERAL_HARNESS` 공통 스킬
> 출력물: 화면 설계 문서(화면 목표, 흐름, 상태, 반응형, 접근성, 시각적 품질 검토, 컴포넌트 선택 근거, 프론트엔드 인계 내용 포함)

---

## 0. Harness Control Rule

- 이 스킬은 `00.HARNESS_RULES.md`의 하위 모듈이다.
- 충돌 시 이 스킬의 절차를 중단하고 `00.QUICK_REF.md`와 `00.HARNESS_RULES.md §3` 우선순위에 따라 상위 규칙을 따른다. 위험 작업 WARN은 사용자 확인 전 스킬 단독으로 진행하지 않는다.
- **이 스킬은 기술 중립적 실행 절차만 소유한다.** 특정 UI 라이브러리(PrimeVue, Tailwind CSS 등)를 고정하는 정책은 이 스킬이 아니라 프로젝트별 Stack Profile(예: `skills/ui-ux-design/STACK_PROFILE_PRIMEVUE_TAILWIND.md`)이 소유한다. 이 스킬 본문에 특정 라이브러리를 전역 규칙으로 하드코딩하지 않는다(외부 검수 반영 — `_PENDING_IMPORT_LIST.md`가 이미 "특정 프론트엔드 스택을 전역 규칙으로 고정하는 것"을 반입 제외 사유로 삼고 있는 것과 같은 원칙).

---

## 1. Trigger

- 새 화면 또는 화면 흐름을 설계할 때
- 기존 화면에 상태(로딩/빈 상태/오류 등)나 반응형 대응이 빠져있을 때
- 화면 설계 결과를 프론트엔드 구현으로 인계해야 할 때
- 화면 설계가 실제 API·데이터로 구현 가능한지 확인이 필요할 때

---

## 2. Do Not Trigger

- 로고·일러스트·브랜드 그래픽 등 순수 그래픽 디자인 제작
- 실제 Vue(또는 프레임워크) 코드 전체 구현(이건 실제 구현 단계이지 설계 단계가 아니다)
- API·DB의 상세 계약 자체를 새로 정의하는 작업(`skills/api-design/SKILL.md` 대상)
- 브라우저 자동화 실행(스크린샷 비교, E2E 테스트 등)
- 프로젝트와 무관한 범용 디자인 이론이나 특정 UI 라이브러리의 전체 사용법 정리

## 3. Required Inputs

프로젝트 어댑터가 있으면 [Project Adapter](../../PROJECT_ADAPTER.md)의 작업 route에서 제품 기준 문서를 먼저 선택한다. 공통 스킬에 제품별 화면·데이터 규칙을 복사하지 않는다. 어댑터가 없으면 아래 입력 기준을 유지한다.

| 입력물 | 필요 이유 |
|---|---|
| 요구사항 또는 사용자 시나리오(SRS 등) | 화면이 풀어야 하는 문제 파악 |
| 대상 사용자와 권한 | 화면별로 누가 무엇을 볼 수 있는지 판단 |
| 화면 목록 또는 사이트맵(있으면) | 전체 구조 파악 |
| 기존 화면 자료(있으면, Figma 등) | 기존 패턴과의 일관성 확인 |
| 브랜드·디자인 토큰(있으면) | 색상/타이포그래피 등 기존 기준 확인 |
| API 명세와 응답 예시(있으면) | 화면이 실제 데이터로 구현 가능한지 확인 |
| 기존 공통 컴포넌트 목록(있으면) | 중복 설계 방지 |
| **프로젝트의 UI Stack Profile** | 어떤 라이브러리가 어떤 역할을 담당하는지 확인(예: `STACK_PROFILE_PRIMEVUE_TAILWIND.md`). Stack Profile이 아직 없는 프로젝트면 이 항목은 N/A로 두고, 화면 설계는 라이브러리 독립적으로 진행한다 |
| 지원 화면 크기와 브라우저(있으면) | 반응형 범위 판단 |

## 4. Procedure

1. 요구사항에서 이 화면(또는 화면 흐름)이 해결해야 하는 사용자 목표를 정의한다.
2. 정상/취소/실패/재시도 등 화면 흐름을 정의한다.
3. 정보와 행동(버튼 등)의 우선순위를 정한다(무엇이 주된 행동이고 무엇이 부차적/파괴적 행동인지).
4. 레이아웃과 시각적 계층을 정한다. 첫 화면에서 사용자가 주된 정보와 행동을 구분할 수 있어야 하며, 모든 요소를 같은 무게로 배치하지 않는다.
5. 기존 디자인 토큰이 있으면 색상, 타이포그래피, 간격, 모서리, 그림자, 아이콘 스타일에 우선 적용한다. 토큰 밖의 선택은 화면 목적에 맞는 이유를 남긴다.
6. 공통 컴포넌트로 해결 가능한 부분과, 프로젝트 Stack Profile이 정의한 컴포넌트 담당 범위를 확인해 컴포넌트를 배정한다.
7. Loading, Empty, Error, Disabled 등 필수 UI 상태를 정의한다.
8. Desktop/Tablet/Mobile 등 반응형 전환 방식을 정의한다.
9. 키보드 접근성, 포커스 순서, 레이블, 색상 외 정보 전달 방식을 확인한다.
10. 기계적·획일적 결과를 막기 위해 다음을 검토한다: (a) 의미 없는 동일 카드·동일 여백의 반복, (b) 핵심 행동보다 장식이 강한 구성, (c) 근거 없는 과도한 그라디언트·글로우·그림자·움직임, (d) 서로 다른 아이콘·타이포그래피·표면 규칙의 혼용, (e) 기능을 설명하지 않는 추상적 마케팅 문구. 의도적인 반복이나 비대칭은 금지하지 않으며, 화면 목적과의 연결 근거를 남긴다.
11. 이 화면에 필요한 API·데이터가 실제로 존재하는지 확인한다(없으면 그 사실을 명시하고 확정 디자인으로 처리하지 않는다).
12. `gates/ui-ux-gate.md` 기준으로 판정한다.
13. 대상이 SRS/화면 목록 기반 상세 검수가 필요하면 `checklists/ui-ux-checklist.md`를 추가 적용한다. 기능·데이터·세션 흐름 설계에는 같은 체크리스트 §1-3을 적용하고 계약 검토와 실제 실행 근거를 구분한다.
14. 프론트엔드가 핵심 동작(상태 전이, 버튼 동작)을 추측하지 않고 구현할 수 있는 수준으로 인계 내용을 정리한다.

## 5. Quality Gate

| 판정 | 기준 |
|---|---|
| PASS | `gates/ui-ux-gate.md` 필수 항목과 시각적 품질 검토 기록이 전부 충족됨 |
| WARN | 일부 보완 사항 또는 시각적 품질 검토의 미해결 항목은 있으나 핵심 동작 판단에는 지장이 없음(위험 WARN은 아래 참고) |
| FAIL | 화면 목적/핵심 행동을 판단할 수 없거나, 시각적 계층 문제로 Primary Action을 식별할 수 없거나, 필요한 API·데이터가 없는데 확정 디자인으로 처리하거나, 모바일에서 핵심 기능 수행이 불가능함 |

**위험 WARN 처리**: 개인정보·권한·결제 관련 화면에서 접근성/보안 관련 정보가 불명확하면 위험 WARN으로 분류하고, 사용자 확인 전 다음 단계로 진행하지 않는다(`04.GATEGUARD.md §6-1` 기준).

## 7. Handoff

이 산출물에 어떤 Gate가 필요한지는 `08.QUALITY_GATE.md`의 §7-2 표가 유일한 SoT다 — 이 스킬은 그 표를 다시 옮겨 적지 않는다. 일반적으로 `gates/ui-ux-gate.md`가 적용되며, 화면 성격에 따라 `gates/security-gate.md`, `gates/payment-gate.md`, `gates/api-gate.md`가 함께 누적될 수 있다.

대상이 SRS/화면 목록 기반이면 `checklists/ui-ux-checklist.md`를 추가 적용한다. 실제 프론트엔드 구현 코드가 존재하면 `skills/verification-loop/SKILL.md`를 항상 함께 적용한다(외부 검수 D-037과 동일 원칙 — 실제 코드가 있으면 Gate만으로 끝내지 않는다). 설계가 끝나고 Vue 3 구현 화면의 다듬기·모션 작업으로 이어지면 `skills/vue-ui-polish/SKILL.md`(스택 한정)를 적용한다. 최종적으로 `06.REPORT_TEMPLATE.md`에 결과를 남긴다.

## 8. Anti-Patterns

- 특정 UI 라이브러리(PrimeVue, Tailwind CSS 등)의 사용 규칙을 이 스킬 본문에 전역 규칙으로 하드코딩하기
- 화면 상태(Loading/Empty/Error) 정의 없이 "정상 흐름"만 설계하고 완료로 보고하기
- 모바일 대응을 "나중에"로 미루고 Desktop만 설계해 넘기기
- 필요한 API·데이터가 없는 상태에서 확정 디자인처럼 다루기
- 프론트엔드가 버튼 동작이나 상태 전이를 추측해야 하는 수준으로 인계하기
- 접근성 확인 없이 색상만으로 정보를 구분하는 설계를 그대로 통과시키기
- 시각적 계층이나 콘텐츠 목적을 설명하지 못한 채 모든 카드·여백·장식을 균일하게 반복하기
- 토큰 또는 선택 근거 없이 여러 색상, 아이콘 스타일, 그림자, 그라디언트, 애니메이션을 섞기
- 기능 설명을 대신하는 "혁신적인", "완벽한", "최고의" 같은 추상적 문구만으로 화면을 채우기
