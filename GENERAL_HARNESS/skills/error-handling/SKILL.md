# Error Handling

> 목적: 예외 처리, 실패 응답, 사용자 메시지, 로그 기준을 정리한다.  
> 사용 위치: `GENERAL_HARNESS` 공통 스킬  
> 출력물: 오류 처리

---

## 0. Harness Control Rule

- 이 스킬은 `00.HARNESS_RULES.md`의 하위 모듈이다.
- 충돌 시 이 스킬의 절차를 중단하고 `00.QUICK_REF.md`와 `00.HARNESS_RULES.md §3` 우선순위에 따라 상위 규칙을 따른다. 위험 작업 WARN은 사용자 확인 전 스킬 단독으로 진행하지 않는다.

---

## 1. Trigger

- API 실패 응답 설계
- 서버 애플리케이션 예외 처리 정리
- 결제/주문/인증 실패 흐름 설계
- 프론트가 처리할 에러 메시지와 백엔드 로그 기준 분리

---

## 2. Do Not Trigger

- 단순 성공 응답만 설명하는 경우
- 화면 문구만 수정하는 경우
- 실패 케이스가 요구사항 범위에 없는 단순 초안 작성

---

## 3. Required Inputs

| 입력물 | 필요 이유 |
|---|---|
| API 명세 | 실패 케이스가 연결될 엔드포인트 확인 |
| 응답 포맷 기준 | 성공/실패 응답 구조 통일 |
| 상태코드 정책 | HTTP 상태와 비즈니스 에러 구분 |

---

## 4. Procedure

1. 실패 케이스를 사용자 실수, 권한 문제, 서버 문제, 외부 연동 문제로 나눈다.
2. 각 실패 케이스에 HTTP 상태코드를 매핑한다.
3. 응답 body 형식을 통일한다.
4. 사용자 메시지와 개발자 로그 메시지를 분리한다.
5. 로그에 민감정보가 포함되는지 확인한다.
6. 관련 API Gate 또는 Security Gate와 연결한다.

---

## 5. Quality Gate

| 판정 | 기준 |
|---|---|
| PASS | 주요 실패 케이스, 상태코드, 응답 body, 사용자 메시지, 로그 기준이 정의됨 |
| WARN | 실패 응답은 있으나 일부 메시지, 로그, 외부 연동 실패 기준이 약함 |
| FAIL | 실패 응답 구조가 없거나 민감정보 로그 가능성이 있고, 프론트가 실패 흐름을 처리할 수 없음 |

---

## 6. Output Format

```md
## Error Handling 결과

- 사용 이유:
- 확인한 입력물:
- 실패 케이스 분류(사용자 실수/권한/서버/외부 연동):
- 상태코드 매핑:
- 사용자 메시지 vs 로그 메시지 분리 여부:
- 민감정보 로그 노출 여부:
- 판단 결과:
- PASS/WARN/FAIL:
- 위험 WARN 여부:
- 다음 연결:
```

---

## 7. Handoff

다음 연결: 실패 케이스가 인증/권한/민감정보와 관련되면 `skills/security-review/SKILL.md`(이 스킬이 `gates/security-gate.md` 판정을 직접 수행한다), API 계약 자체(상태코드/응답 형식)와 관련되면 `gates/api-gate.md`도 함께 적용한다(둘 다 해당하면 둘 다) → `06.REPORT_TEMPLATE.md`

---

## 8. Anti-Patterns

- 모든 실패를 500으로 처리하기
- 사용자에게 내부 예외 메시지를 그대로 보여주기
- 비밀번호, 토큰, 결제키 같은 민감정보를 로그에 남기기
- 실패 응답 없이 정상 흐름만 문서화하기
