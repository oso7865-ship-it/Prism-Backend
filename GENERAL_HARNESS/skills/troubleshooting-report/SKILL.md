# Troubleshooting Report

> 목적: 다음 작업자가 같은 문제를 재현하고 해결 근거와 남은 조치를 이해할 수 있게 기록한다.
> 사용 위치: GENERAL_HARNESS 공통 스킬
> 출력물: 표준 작업 Report 안의 트러블슈팅 기록

## 0. Harness Control Rule

- 이 스킬은 `00.HARNESS_RULES.md`의 하위 모듈이다.
- 충돌 시 이 스킬의 절차를 중단하고 `00.QUICK_REF.md`와 `00.HARNESS_RULES.md §3` 우선순위에 따라 상위 규칙을 따른다. 위험 작업 WARN은 사용자 확인 전 스킬 단독으로 진행하지 않는다.

## 1. Trigger

- 사용자가 트러블슈팅 보고서·장애 회고·원인 및 해결 과정 기록을 요청한다.
- 반복 실패, 환경 차이, 여러 해결 시도 또는 미해결 원인을 다음 작업자에게 인계해야 한다.
- 복구한 장애에 대해 재현 조건·검증 증거·후속 조치를 보존해야 한다.

## 2. Do Not Trigger

- 장애 없는 일반 기능 구현이나 간단한 오탈자 수정.
- 에러 응답 설계만 필요한 경우: error-handling의 역할이다.
- 즉시 복구가 우선인 장애에서 보고서 완성을 복구의 선행 조건으로 삼지 않는다. 관측 메모를 남긴 뒤 복구 흐름을 따른다.

## 3. Required Inputs

| 입력 | 용도 |
|---|---|
| 발생 환경·시점·대상 버전 및 위치 | 다른 환경·커밋의 결과와 혼동 방지 |
| 증상·기대 결과·로그 또는 사용자 관측 | 실제 영향과 실패 조건 확인 |
| 재현 단계·시도·수정 diff·검증 결과 중 확보한 자료 | 원인과 해결의 인과관계 확인 |
| 기존 작업 Report와 프로젝트 기록 경로 | 중복 기록 방지 및 인계 |

자료가 없는 항목은 미확인과 필요한 확인 방법을 적는다. 추측으로 빈칸을 채우지 않는다.

## 4. Procedure

1. 기존 Report와 로그에서 사건을 구분한다. 여러 독립 원인이 있으면 사건별로 나누고, 재발이면 이전 기록을 연결한다.
2. 아래 여섯 항목을 작성한다. 시각에는 시간대를 적고 모르면 미확인으로 남긴다. 위치는 저장소 기준 상대 경로·함수·API·CI job 등 다음 작업자가 찾을 수 있는 단위로 적는다.
3. 관측 사실과 원인 가설을 분리한다. 직접 원인, 촉발 조건, 기여 요인을 확보된 근거 범위에서 설명한다. 오류 문구만 반복하거나 개인 실수로 분석을 끝내지 않는다.
4. 실패한 시도도 순서·의도·결과와 함께 남긴다. 임시 우회와 근본 수정을 구분하고, 왜 해당 수정으로 실패 조건이 바뀌는지 설명한다.
5. 같은 재현 조건의 수정 전후 결과와 필요한 회귀 검증을 연결한다. 로컬·CI·운영 검증 범위를 구분하고, 해결 검증이 없으면 해결 완료로 적지 않는다.
6. 후속 조치를 원인과 연결하고 담당자·기한 또는 실행 조건·완료 기준·상태를 남긴다. 담당자나 기한이 미정이면 미정으로 표시한다. 이미 적용한 예방책과 제안을 구분한다.
7. `06.REPORT_TEMPLATE.md`의 헤더·상태·게시 절차를 유지하며 발견된 문제 아래에 기록한다. 긴 사건은 별도 표준 Report로 분리하고 원래 작업 Report에는 링크만 둔다. 토큰·개인정보·내부 자격증명은 제거하고 필요한 로그만 인용한다.

## 5. Quality Gate

| 판정 | 기준 |
|---|---|
| PASS | 여섯 항목이 증거 또는 명시적 미확인으로 채워져 있고, 원인 확실성·해결 검증·후속 조치 상태를 구분하여 인계 가능 |
| WARN | 환경·재현·원인·후속 담당자 등 중요한 정보가 미확인이며 다음 확인 방법이 기록됨. 장애 해결 완료를 주장할 수 없음 |
| FAIL | 가설을 확정 원인으로 서술, 검증 없이 해결 완료 주장, 실패 시도 은폐, 후속 제안을 적용 완료로 표현, 비밀값 포함 |

이 판정은 기록 품질이다. 문서 PASS가 미해결 장애나 실패한 실행 검증을 해제하지 않는다.

## 6. Output Format

기존 Report의 발견된 문제 아래에 다음 블록을 넣는다. 여러 사건이면 제목에 사건 식별자를 붙인다.

```md
### 트러블슈팅: {증상을 드러내는 제목}

- 사건 상태: 조사 중 / 임시 우회 / 해결 검증 완료 / 미해결 종료
- 원인 상태: 가설 / 확인 / 미확인
- 관련 이슈·Report·커밋·PR: 확인된 링크 또는 미확인

#### 어디서 발생했나
- 환경·버전·발생/발견 시각(시간대):
- 저장소·파일·함수·API·job 등 위치:

#### 어떤 문제가 있었나
- 기대 동작과 실제 증상·오류:
- 영향 범위·지속 시간(모르면 미확인):
- 관측 근거(민감정보 제거):

#### 어떻게 발생했나
- 사전 조건·입력·재현 순서:
- 발생 흐름·재현 여부 및 빈도:

#### 왜 발생했나
- 직접 원인·촉발 조건·기여 요인:
- 원인을 뒷받침하는 증거와 배제한 가설:
- 남은 가설·미확인 및 다음 확인 방법:

#### 어떻게 해결했나
| 순서 | 시도와 이유 | 변경 위치·내용 | 결과·증거 |
|---|---|---|---|
| 1 | 실제 수행한 시도 | 실제 변경 또는 변경 없음 | 성공/실패/미확인 |

- 채택한 해결책과 작동 이유:
- 임시 우회인지 근본 수정인지:
- 검증 환경·대상 버전·명령/시나리오·기대/실제 결과:
- 검증하지 못한 범위·잔여 위험:

#### 앞으로 어떻게 대응하나
| 조치 | 원인과의 연결 | 담당자 | 기한/실행 조건 | 완료 기준 | 상태 |
|---|---|---|---|---|---|
| 예방·탐지·재발 시 복구 중 필요한 조치 | 해결할 실패 조건 | 지정 또는 미정 | 날짜·조건 또는 미정 | 확인 가능한 결과 | 제안/예정/진행/완료 |
```

## 7. Handoff

- 추가 진단·복구가 필요하고 발동 조건에 맞으면 `skills/agent-recovery/SKILL.md`.
- 수정 결과 검증은 `skills/verification-loop/SKILL.md`, 재발 테스트 설계가 필요하면 `skills/test-design/SKILL.md`.
- 구조·기술 선택이 바뀌었으면 프로젝트의 ADR 규칙으로 결정을 연결한다. 모든 오류마다 ADR을 만들지 않는다.
- 게시·현재 상태 연결은 `06.REPORT_TEMPLATE.md` → `05.WORKING_CONTEXT.md` → `skills/report-consistency/SKILL.md`. 외부 공유·Git 쓰기는 기록 요청만으로 자동 실행하지 않는다.

## 8. Anti-Patterns

- “에러 발생 → 수정 완료”만 적어 재현·원인·검증을 잃기.
- 로그 전체를 붙이고 정작 핵심 오류·해결 위치를 적지 않기.
- “주의하겠다”, “테스트 강화”처럼 완료 기준 없는 예방책만 적기.
- 과거 사건을 지금 재검증한 것처럼 쓰거나, 새 정책을 과거 수행 사실로 소급하기.
- 보고서 작성 요청을 운영 환경 변경·재현 실행 허가로 해석하기.
