# 06. REPORT TEMPLATE

> 한국어 별칭: 작업 리포트 표준  
> 목적: 작업 후 변경 내용, 검증 결과, 미해결 항목을 같은 형식으로 남긴다.  

---

## 1. 리포트 작성 시점

다음 경우에는 리포트를 남긴다.

- 여러 파일을 수정했을 때
- Gate를 통과해야 하는 산출물을 만들었을 때
- 결제/보안/DB/API 관련 변경을 했을 때
- 자동 검증 스크립트를 실행했을 때
- WARN/FAIL이 발생했을 때
- 실패/중단 후 재개한 작업을 처리했을 때
- 외부 감사/검수 피드백을 반영했을 때

---

## 2. Report와 Working Context 책임 분리

| 구분 | Report | Working Context |
|---|---|---|
| 목적 | 작업 단위 증거 | 현재 상태 요약 |
| 기록 범위 | 변경 파일, 검증 명령, 위험도, 판정 근거, 미해결 항목 | 다음 작업에 필요한 결정과 큐 |
| 보관 방식 | `reports/YYYY-MM-DD_{작업명}_report.md` (같은 날짜에 여러 Report가 예상되면 `HHMM` 접미사 권장) | `05.WORKING_CONTEXT.md`에 요약 갱신 |
| 중복 방지 | 상세 내용을 보관 | Report 링크/요약만 기록 |

## 3. 리포트 유형 선택 기준

| 리포트 유형 | 사용 시점 | 필수 시작 섹션 |
|---|---|---|
| 일반 작업 리포트 | 생성/수정/검증 작업을 수행한 뒤 | `0. 작업 범위 확인` |
| 감사/검수 리포트 | 문서 세트, 코드, 산출물을 비판적으로 검수할 때 | `0. 검수 범위 확인` |
| 패치 리포트 | 외부 피드백을 반영해 수정한 뒤 | `0. 작업 범위 확인` + 피드백 출처 |

트러블슈팅 기록 요청 또는 인계할 실패 분석이 있으면 `skills/troubleshooting-report/SKILL.md`의 여섯 항목(위치·증상·발생 과정·원인·해결·후속 조치)을 발견된 문제 아래에 작성한다. 긴 사건은 별도 표준 Report로 분리해 연결한다. 이 문서의 헤더·단계별 상태·게시 절차는 그대로 적용한다. 단순 오류마다 상세 회고를 강제하지 않는다.

감사/검수 리포트는 확인하지 못한 문서와 검수 한계를 반드시 적는다. 일반 작업 리포트는 수정 대상과 검증 방법을 먼저 적는다.

## 5-1. Git 이력 기록 규칙

헤더의 "작업 브랜치"와 "커밋/PR"은 추측으로 채우지 않는다. Report 작성 시점에 실제 명령으로 확인해서 채운다.

| 칸 | 확인 명령 | 허용 값 |
|---|---|---|
| 작업 브랜치 | `git branch --show-current` | 실제 브랜치명. Git 저장소가 아닌 것을 `git status`로 확인한 경우에만 "미사용" |
| 커밋/PR | `git log -1 --oneline` 또는 PR 링크 | 커밋 해시/PR 링크. 아직 커밋 전 초안이면 "미커밋"으로 적고 커밋 후 갱신 |

- "미사용"이라고 적으려면 `git status` 실행 결과가 근거로 있어야 한다. 이 확인 없이 "Git 저장소가 아니다"라고 서술하는 것을 금지한다(실사용 검수 P-02 재발 방지).
- 구조/파일 이동 작업(L/XL)은 되돌릴 기준 커밋을 기록한다. 미커밋 상태에서는 확인한 구현·로컬 검증 결과만 보고하고 전체 완료·공식 반영으로 표현하지 않는다. 기록을 완료하기 위해 요청하지 않은 Git 쓰기를 수행하지 않는다.

### 5-1a. 단계별 상태와 증거

새 작업 기록은 템플릿의 상태 기록 버전 1을 사용한다. 구현·로컬 검증·병합·배포·실제 연동은 독립된 관측 결과이며 앞 단계 완료가 다음 단계 완료를 뜻하지 않는다. 보고서에 단독으로 "완료"라고 쓰지 않고 어느 단계인지 명시한다.

| 상태 항목 | 완료 근거에 포함할 내용 |
|---|---|
| 구현 | 요구 범위, 변경 파일·diff 또는 구현 커밋 |
| 로컬 검증 | 명령, 종료 결과, 검사 범위·개수, 증거 파일. 로컬 검증 대상에 검사한 커밋 또는 working-tree 변경 범위를 식별 |
| 병합 | PR 또는 병합 사건, 실제 base 브랜치, merge commit, 관측 시각. 병합 대상은 설정의 remote/integrationBranch와 일치 |
| 배포 | 환경, 배포 실행 ID·아티팩트 버전, 실행 성공 결과 |
| 실제 연동 | 실제 대상 환경, 검증 시나리오, 요청·관측 결과, 관측 시각. mock·단위 테스트와 구분 |

허용 상태는 완료 / 진행 중 / 미수행 / 미확인 / 해당 없음 / 실패다. 미수행은 이번 작업에서 수행하지 않았음을 아는 경우, 미확인은 수행 여부나 결과를 확인하지 못한 경우다. 완료·실패에는 관측 근거가, 해당 없음에는 작업 범위상 제외하는 이유가 필요하다. 보고 시점 상태 확인 시각을 시간대가 포함된 ISO 8601 형식으로 남긴다. 기록 후 코드가 바뀌면 과거 검증 근거를 새 코드에 그대로 적용하지 않고 대상과 상태를 재판정한다.

상태 기록 검사는 `scripts/validate-work-records.mjs`가 담당한다. 버전 1 선언 또는 단계 상태 필드가 있으면 5단계·시각·필요 근거를 확인한다. legacy 표시는 이 검사를 면제하지 않는다. 새 상태 필드가 없는 과거 문서는 자동 변환하지 않으며 기존 형식 검사를 유지한다. 근거 문자열의 존재는 사실 인증이 아니다. 단순 TODO·미확인·placeholder는 완료 근거로 인정하지 않으며, 구체적인 근거의 타당성은 수동 검수한다.

### 5-1b. 프로젝트 Git 설정

프로젝트 루트 harness.config.json의 형식은 schemaVersion: 1, git.remote, git.integrationBranch다. 두 Git 값은 필수이며 이 HARNESS 저장소에서는 origin과 main이다. 다른 프로젝트의 dev 또는 release 계열 운영은 그 프로젝트의 명시된 정책에 맞게 설정한다. 현재 브랜치·원격 HEAD·원본 하네스의 설정을 자동 대체값으로 사용하지 않는다.

설정이 없으면 기존 문서의 일반 검사는 가능하지만 버전 1 기록에서 병합 완료를 주장할 수 없다. 손상된 JSON·지원하지 않는 버전·알 수 없는 키·빈 값·지원하지 않는 이름은 FAIL이다. 이름은 영문·숫자 시작을 사용하며 remote는 영문·숫자·하이픈·밑줄, 브랜치는 여기에 점·슬래시를 허용하되 Git 예약·위험 형태를 제한한다. 이 형식 검사는 실제 ref 존재 확인을 대신하지 않는다. 특수 문자 브랜치 등 지원 범위 밖은 설정을 임의로 치환하지 말고 지원 여부를 먼저 검토한다.

### 5-1c. Git 사건 후 기록 동기화

commit, push, PR 생성, 병합은 서로 다른 사건이다. 각 사건 뒤에는 다음 순서로 갱신한다.

1. 실제 명령·API 결과에서 사건과 대상을 확인한다. 현재 HEAD가 있다는 이유만으로 이번 변경이 커밋됐다고 판단하지 않는다. fetch하지 않은 remote-tracking ref는 원격 최신 상태로 단정하지 않는다.
2. 현재 상태를 주장하는 작업 계획, 현재 Report, 최신 포인터, 작업 큐를 식별한다. Git 제외 로컬 문서도 포함한다.
3. 사건·관측 시각·대상 커밋/브랜치/PR·성공/실패·확인 수단을 남긴다. PR 생성은 병합 완료가 아니다. squash/rebase 병합은 원래 feature SHA의 ancestry만으로 판정하지 않고 PR의 merged/base/merge commit 증거를 확인한다.
4. 해당 사건으로 달라진 항목만 갱신한다. 미요청 push·병합·배포를 기록 완성 목적으로 실행하지 않는다. 계획/Report와 최신 포인터가 다른 이력을 가리키면 각각의 소유 범위를 유지한다.
5. 일부 기록 갱신 실패 시 이미 성공한 사건은 보존하고, 미갱신 파일·관측 사실·다음 확인 절차를 Handoff Note로 남긴다. 전체 동기화 완료로 보고하지 않는다.

| 사건 | 최소 기록 |
|---|---|
| commit | 이번 변경이 포함된 커밋, 남은 working-tree 변경 |
| push | 대상 remote/branch와 실제 push 결과, 공유된 커밋 |
| PR 생성 | PR 식별자, head/base, open/merged 상태를 구분한 관측 |
| 병합 | 설정 기준 브랜치와 일치하는 base, 실제 병합 상태·merge commit |

과거 기록에서 확인할 수 없는 Skill·Gate·Git 결과는 추측으로 보충하지 않는다. 사실 복원이 불가능하면 별도 정정/인계 기록에 legacy와 확인 한계를 남긴다. 과거 기록 전체를 현재 상태로 다시 쓰거나 새 정책을 과거 사실에 소급 적용하지 않는다.

## 5-2. 프로젝트 상수와 반복 미해결 항목

여러 Report에서 같은 미해결 항목이 반복되면(예: "자동화 테스트 미구축") 그것은 작업 단위 문제가 아니라 프로젝트의 장기 제약이다.

- 이런 항목은 `05.WORKING_CONTEXT.md §1-1`에 **프로젝트 상수**로 한 번만 기록한다.
- 프로젝트 상수로 기록된 항목은 이후 Report의 검증 결과·미해결 항목에 반복 기재하지 않는다. 해당 상수가 이번 작업 위험도 판정을 바꾸는 경우에만 한 줄로 참조한다.
- 프로젝트 상수가 해소되면(예: 테스트 환경 구축) Working Context에서 제거하고, 해소를 다룬 Report에 그 사실을 남긴다.

## 5-3. 후속 작업 누적 처리 규칙

한 세션에서 작업이 이어질 때 표준 8개 섹션 뒤(§9 이하)에 후속 작업을 덧붙일지, Report를 분리할지는 아래 기준으로 판단한다.

| 상황 | 처리 |
|---|---|
| 후속 작업이 앞선 검증 결과를 무효화하지 않는 보완 | §9 이하 누적 허용. 각 섹션에 작업 시각과 검증 결과를 함께 남긴다 |
| 후속 작업이 앞선 §3 검증 결과를 하나라도 무효화 | **별도 Report로 분리**하고 원래 Report에 superseded 표시(§8) |
| 무효화가 일부 항목에 그침 | 누적은 허용하되, 무효화된 검증 항목 원문에 "superseded — §N 참조" 표기를 남긴다 |

한 Report가 자기 검증 결과를 표기 없이 스스로 무효화한 채 남아 있으면 안 된다.

## 5-4. 위험도–Gate 불일치 사유 명시

헤더 위험도가 "일반"이 아닌데 적용 Gate가 "해당 없음"이면, `0. 작업 범위 확인`의 근거 행에 그 사유를 명시해야 한다. 사유 없는 "해당 없음"은 Report 검증에서 WARN으로 처리한다. 구조 작업은 `04.GATEGUARD.md §6-1` 기준 확인 기록도 함께 남긴다.

## 6. 판정 기준

의미와 WARN 분기 기준은 `08.QUALITY_GATE.md §2`가 소유하며, 이 문서는 표를 복제하지 않는다. Report에서는 PASS/WARN/FAIL 판정 결과와 근거만 기록하고, 판정 기준 자체는 `08.QUALITY_GATE.md`를 참조한다.

세부 PASS/WARN/FAIL 의미와 WARN 분기 기준의 소유 문서는 `08.QUALITY_GATE.md`다. 이 문서는 현재 작업에서 필요한 실행 요약만 둔다.

## 7. Checklist 결과 이관 규칙

체크리스트를 사용했다면 결과를 Report에 옮긴다.

| Checklist 결과 | Report 처리 |
|---|---|
| 모두 충족 | PASS 근거에 기록 |
| 일부 미충족이지만 위험 낮음 | WARN으로 기록하고 미해결 항목에 남김 |
| 필수 항목 누락 또는 위험 높음 | FAIL로 기록하고 다음 단계 진행 금지 |

## 8. 과거 Report superseded 표시 규칙

새 Report가 이전 Report의 다음 작업이나 상태 판단을 대체하면 이전 Report 상단에 아래 형식의 superseded 표시를 추가한다.

```md
> Superseded note:  
> 이 보고서의 다음 작업 판단은 `reports/_LATEST.md`가 가리키는 최신 Report로 대체되었다.  
> 과거 의사결정 근거로는 유효하지만, 현재 Next Work 판단은 최신 Report와 `05.WORKING_CONTEXT.md`를 우선한다.
```

**특정 후속 Report 파일명을 직접 쓰지 않고 `reports/_LATEST.md`를 가리킨다.** 구체적 파일명을 쓰면 그 파일이 나중에 `reports/archive/`로 이동했을 때 경로가 깨지기 때문이다(과거 여러 Report에서 실제로 발생한 문제 — 외부 검수 M-04). 이미 있는 과거 Report의 구체적 경로 인용은 굳이 소급해서 고치지 않는다. 원본 그대로 두고 `reports/archive/HISTORY_DIGEST.md`로 대신 추적한다.

원칙:

- archive로 옮긴 Report는 기본적으로 원본을 보관하지만, **원본 삭제는 금지되지 않는다.** 삭제하려면 `reports/archive/HISTORY_DIGEST.md`에 요약이 먼저 남아 있어야 하고, 삭제 사실을 `HISTORY_DIGEST.md`의 "삭제 이벤트"(`PURGE_EVENT` 블록)로 기록해야 한다(외부 검수 m-01, 3회차 자체검수 — 삭제 이벤트 모델(ADR-034) 도입 이후에도 이 문장이 옛 용어 "삭제 로그 표"를 그대로 쓰고 있었다). 삭제는 파일 손상 가능 작업이라 `04.GATEGUARD.md §6-1` 기준대로 사용자의 실시간 확인이 항상 필요하다(예외 없음, 사용자 결정 완료 — ADR-031).
- 다음 작업 판단은 최신 Report와 `05.WORKING_CONTEXT.md`를 우선한다.
- 같은 날짜 Report가 여러 개 있으면 `reports/_LATEST.md`를 먼저 확인한다.
- Working Context의 현재 상태와 최신 Report의 상태가 다르면 먼저 동기화한다.

---

## 8-1. Superseded Report 보관 규칙

Superseded 표시가 붙은 Report는 `reports/` 최상위에서 `reports/archive/`로 이동한다. **기본은 삭제가 아니라 이동이며 내용을 그대로 유지하는 것("retained" 상태)이지만, `§8`에서 설명한 삭제 예외 조건(요약 선행 보존 + 삭제 이벤트 기록 + 사용자 실시간 확인)을 충족하면 원본을 나중에 삭제할 수 있다("purged" 상태) — 이 경우 `reports/archive/HISTORY_DIGEST.md`의 PURGE_EVENT 기록이 유일한 근거가 된다(외부 검수 M-07/X-07).**

- 목적: 일상적인 작업에서 `reports/` 폴더를 훑어볼 때 활성 Report만 보이게 해서, 이미 대체된 기록까지 매번 다시 읽는 것을 줄인다.
- 이동 시점: superseded 표시를 추가하는 시점에 함께 이동한다(별도 일정으로 미루지 않는다).
- `reports/_LATEST.md`, `reports/README.md`는 이동 대상이 아니다.
- **근거가 필요해 과거 Report를 확인할 때는 먼저 `reports/archive/`에 실물이 있는지 확인한다. 없으면(purged) `reports/archive/HISTORY_DIGEST.md`의 해당 PURGE_EVENT를 찾아 그 안의 한 줄 요약으로 대신한다 — 원본의 상세 내용은 재현할 수 없다.**

## 8-2. Git 기반 Report 완료 트랜잭션

이 절은 하네스 자체와 부착된 프로젝트의 Report에 공통 적용한다. Git 저장소가 변경 이력의 Source of Truth이며, **프로젝트 설정의 기준 브랜치로 확인된 병합만 공식 반영**이다. 배포는 별도 증거로 확인한다. 작업 브랜치 push는 공유 가능한 진행 상태일 뿐 공식 반영이 아니다.

```text
1. Report 초안을 작성한다. `reports/_LATEST.md`는 아직 그대로 둔다.
2. 작업 계약의 검증(관련 Gate, Checklist, 빌드·테스트, 하네스 자체 변경이면 적용 가능한 scripts)을 실행한다.
3. FAIL이면 멈춘다. 원인을 고친 뒤 검증과 초안 작성부터 다시 한다. 일반 WARN은 Report에 기록할 수 있지만, 구조·위험 WARN은 근거나 사용자 확인 전 진행하지 않는다.
4. 검증을 통과하면 최신성 문서를 원자적으로 갱신한다.
   a. `reports/_LATEST.md`를 새 Report로 전환한다.
   b. 이전 Report가 같은 작업 단위의 최신 Report이면 superseded 표시 후 archive로 이동하고 `HISTORY_DIGEST.md`를 갱신한다. 하네스와 프로젝트의 첫 Report 전환처럼 서로 다른 이력은 이동하지 않는다.
   c. L/XL 또는 다음 작업 판단에 영향을 주는 경우 Working Context를 갱신한다.
5. 커밋·push·PR·병합은 각각 요청된 범위에서만 수행한다. 미요청 단계는 미수행으로 남기며 로컬 구현·검증 결과를 별도로 보고한다.
6. Git 사건마다 아래 §5-1의 동기화 절차를 적용한다. 설정된 기준 브랜치와 일치하는 실제 병합 증거가 있을 때만 공식 반영으로 판단한다. push 전은 로컬 작업 상태, push 후는 공유 진행 상태다.
7. 실패·중단 시 실패한 단계와 미완료 기록을 남기며 전체 완료로 보고하지 않는다. 이미 성공한 Git 사건은 취소된 것처럼 기록하지 않는다. 최신성 문서가 일부만 갱신되면 현황·갱신할 파일·남은 확인을 Handoff Note에 남기고 다음 작업 전 정합화한다.
```

사용자가 ZIP export를 별도 요청한 경우에만 이 흐름의 검증 단계에서 `scripts/validate-package.mjs --zip <후보 경로>`를 추가한다. ZIP 검증은 export 품질만 보장하며 Git 공식 반영 기준을 바꾸지 않는다.

## 9. 리포트 파일명 규칙

```txt
reports/YYYY-MM-DD_{작업명}_report.md
```

예시:

```txt
reports/2026-06-25_payment-gate-review_report.md
```

같은 날짜에 Report가 여러 개 생기면 파일명에 `HHMM`을 붙이는 것을 권장하고, `reports/_LATEST.md`에 현재 판단 기준 Report를 명시한다.
